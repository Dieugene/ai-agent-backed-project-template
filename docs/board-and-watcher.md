# Board and Watcher

Два инструмента наблюдаемости пула поверх [pool-шины](pool-communication.md):

- **Вотчер** (`pool watch`) — фоновый «спящий» процесс, который **будит**
  простаивающего агента на входящую задачу, не тратя его контекст;
- **Борд** (`pool board`) — живая доска: кто из агентов жив, у кого взведён
  вотчер, кто сейчас работает, у кого что в ящике.

> Описание паттерна, не инструкция под проект. Идентификаторы —
> плейсхолдеры (`<bus>`, `<owner>`, `<pool-name>`, `<role>-<scope>`).
> Рабочий код: борд/вотчер/активность — подкоманды общей
> [../scripts/pool.ps1](../scripts/pool.ps1); отдельные скрипты —
> [../scripts/board-window.ps1](../scripts/board-window.ps1),
> [../scripts/notify-pool-idle.ps1](../scripts/notify-pool-idle.ps1).

Базовый механизм шины (сообщение = файл, адрес = папка `<bus>/<owner>/new/`,
`[POOL INBOX]`-баннер, lifecycle) описан в
[Pool Communication](pool-communication.md); здесь — только надстройка
наблюдаемости.

---

## 1. Вотчер (`pool watch`)

### Push поверх pull

Hook `[POOL INBOX]` даёт **pull**: агент видит входящие только когда сам
отправляет промпт. Вотчер — опциональное **push**-дополнение: будит
простаивающую сессию при входящей задаче, **не тратя контекст на ожидание**
(сон идёт в shell-процессе, не в модельном цикле). Pull-баннер остаётся
всегда и **страхует** вотчер: промах push покрывается баннером на следующем
ручном промпте.

### Механика

`pool watch` — фоновый вотчер на **одного** агента (`Owner`/`BusRoot` из
env). Запускается **из сессии агента** фоновой задачей
(`Bash run_in_background: true`), спит (`Start-Sleep`) и на каждом цикле:

- переписывает свой **heartbeat-lock** `<bus>/.watch/lock-<owner>.txt`
  (доказательство «я жив»);
- проверяет `<bus>/<owner>/new/` на **новое** (сверяясь с ledger, ниже);
- на новом сообщении **снимает lock, печатает доклад и завершается** →
  харнесс будит сессию. На пустом — снова спит.

Вотчер **read-only** по шине (сообщений не трогает). Всё его состояние —
внутри `<bus>` (gitignored):

```
<bus>/.ledger/seen-<owner>.txt    # что уже «отстреляно» (идемпотентность)
<bus>/.watch/lock-<owner>.txt     # heartbeat-lock (singleton)
```

Это **встроенный режим** той же pool-CLI, что и `send`/`hook`/`board` —
отдельных скриптов-вотчеров нет.

### Два инварианта корректности

1. **Супрессор повторного пробуждения — `claim`, не ledger (для задач).**
   Задача будит каждый свежий вотчер, пока лежит в `new/`; уводит её `claim`
   (в `cur/`) — тогда новый вотчер её уже не видит. Ledger держит **только**
   `note-wake` (одноразовый пинок: помечается до выхода, повторно не будит).
   Так задача, разбудившая раз, но не заклеймленная, не застревает немой.
2. **Один вотчер на owner — «новейший побеждает».** Lock несёт
   `<pid>|<StartTime-ticks>|<iso>` и обновляется каждый цикл. При взводе новый
   вотчер читает pid из lock'а и, если тот процесс **реально жив** (pid запущен
   И StartTime совпадает — защита от переиспользования pid), **сносит его**
   (`Stop-Process`) и встаёт сам. Прежнее «свежий lock → сразу выйти» **убрано**
   — оно давало осиротевшему вотчеру блокировать настоящий. Живость теперь по
   **процессу**, не по свежести lock'а (свежий lock орфана врал про
   доставляемость). Следствия: агент не само-проверяет «а не взведён ли уже» —
   просто взводит, лишний снесётся; в норме сносить некого (отработавший вотчер
   уже вышел).

### Переживает `/compact`, но перевзвод — обязанность агента

Взведённый вотчер **переживает `/compact`** (это shell-процесс, он живёт
вне модельного цикла). Но разбудить idle-сессию может **только** фоновая
задача, запущенная **инструментом агента**, в момент её exit. Процесс,
поднятый иначе (hook, внешний `.bat`, само-spawn), харнесс с сессией не
свяжет. Отсюда структурное правило:

> **Перевзвод вотчера обязан быть действием агента.** Порядок при пробуждении —
> **`claim` → перевзвод → работа** (именно так): сперва (ШАГ 1) `claim` задачи
> (уходят из `new/` в `cur/`), затем (ШАГ 2) перевзвод вотчера, затем (ШАГ 3)
> работа. `claim` первым, не перевзвод: заклеймленная задача уходит из `new/`, и
> свежий вотчер по ней не сработает; перевзвод ДО claim заставил бы новый вотчер
> снова увидеть её в `new/` и будить по кругу (агент перевзводит без конца).
> Доклад сработавшего вотчера печатает `claim` как ШАГ 1 (primacy-гейт).

На возобновлении/после `/compact` агент просто **взводит заново** — «новейший
побеждает» снесёт прежний, если тот ещё жив (само-проверка свежести больше не
нужна). **Никогда не взводить вотчер ИЗ субагента** — он осиротеет (основную
сессию не будит + блокирует её взвод); это источник орфана, который закрывает
Stop-хук арм-гейт (ниже).

### Stop-хук арм-гейт: детерминированный взвод

Взвод вотчера переносится с «дисциплины агента» на **хук** — чтобы сессия не
могла уйти в idle без живого вотчера, и чтобы убрать источник орфана (вотчер,
случайно взведённый из субагента).

- **Триггер — `Stop`-хук основной сессии** (глобальный
  `<user-home>\.claude\settings.json`, команда `pool.ps1 armgate`). На
  завершении хода: нет живого вотчера → хук отдаёт **exit 2 + сообщение в
  stderr** с командой взвода → харнесс придерживает ход и передаёт текст
  агенту, тот взводит вотчер (в **основном** контексте → wake-способный,
  трекнутый). Есть живой → exit 0, ход закрывается штатно.
  > На `Stop`-хуке до модели доходит именно **exit 2 + stderr**; `reason` в
  > stdout виден только пользователю — поэтому механизм завязан на exit-коде.
- **Только `Stop`, не `SubagentStop`** → субагент взвод не инициирует. Это и
  закрывает источник орфана: вотчер, взведённый из субагента, осиротел бы.
- **Живость — прямой проверкой процесса** (pid+StartTime из lock'а), не
  свежестью heartbeat'а.
- **Опт-ин по env `POOL_WATCHER=1`** — хук глобальный, но первой строкой
  проверяет флаг; нет → мгновенный no-op. Флаг ставят **launch-скрипты только
  вотчерным ролям** (гейт `if ($InitialPromptFile) { $env:POOL_WATCHER='1' }`
  — вотчерные роли передают `-InitialPromptFile`, watcherless нет).
  DevOps/серверные/plain — без флага, хук молчит.
- **Анти-wedge:** взвод не поднялся за ход и повторно нет вотчера <30с → хук
  НЕ блокирует снова (stderr-предупреждение, exit 0); плюс встроенный лимит
  цикла харнесса. Сломанный spawn (антивирус) сессию не заклинит; ошибка гейта
  → exit ≠2 → fail-open.

**Активация — на рестарте сессии** (хук и флаг читаются при старте). До
рестарта роль работает по прежней ручной дисциплине перевзвода — обратно
совместимо. Реализация — `Invoke-ArmGate` + newest-wins `Invoke-Watch` в
[../scripts/pool.ps1](../scripts/pool.ps1).

### Push задачи повторяется до claim; note-wake — одноразовый

**Задача** будит каждый свежий вотчер, **пока лежит в `new/`** — супрессор это
`claim` (уводит её в `cur/`), а не факт срабатывания. Раньше вотчер штамповал id
в ledger в момент **срабатывания** (не взятия), и задача, разбудившая раз, но не
заклеймленная (агент занят / wake потерян / перевзвод ДО claim), **страндилась**
в `new/` немой — push по ней не повторялся. Теперь этой ямы нет: незаклеймленная
задача продолжает будить каждый перевзвод, а `claim` её замолкает. **`note-wake`**
остаётся **одноразовым** (разовый пинок, закрывается `dismiss`, а не `claim`): его
id ledger помнит, повторно он не будит. Pull-баннер `[POOL INBOX]` — по-прежнему
пол под всё: даже промах push виден на следующем ходу агента.

### Watcherless-роли — намеренно без вотчера

Взвод вотчера — **НЕ** универсальная установка. **DevOps и серверные роли
держат без вотчера намеренно**: они проверяют входящие **по прямой команде
пользователя**, не автономно. Причина — серверные/деплой-операции
пользователь контролирует лично; автономное пробуждение обошло бы этот
контроль.

Практика:

- не вшивай «взведи вотчер на старте» безусловно в общий онбординг — делай
  это **по политике роли**; для DevOps/серверных явно «вотчер не запускай»;
- доставка таким агентам всё равно работает: `POOL_BUS_ROOT` в их wrapper'е
  стоит, `[POOL INBOX]` (pull) показывает входящие каждый ход, когда
  пользователь их промптит — push тут просто не нужен;
- не уверен про конкретную роль — спроси пользователя.

### Терминология: «вотчер» зарезервировано за inbox-watcher'ом

Слово **«вотчер»** (в баннерах, логах, видимых пользователю именах
процессов) — **только** про этот inbox-watcher на входящие задачи. Агенты
часто заводят собственные **доменные** фоновые сторожа (ждать новый прогон,
появление файла, внешнее событие) — их **нельзя** называть «watcher» в
user-facing выводе, иначе путаница: пользователь видит «висящий» процесс с
надписью `WATCHER` и решает, что взведён нотификатор задач, хотя это другое.
Доменные сторожа называть иначе: `RUN-WATCHER`, `batch-watcher`,
`run-sentinel`, `*-poller`.

> **Жалоба «вотчер не сработал» → первым делом проверить свежесть
> `<bus>/.watch/lock-<owner>.txt`**, а не любой фоновый процесс. Свежий
> lock = вотчер жив и спит; протухший = умер/завис; нет файла = не взведён
> (или краткий зазор fire→re-arm). «Висит фоновый процесс» ≠ «взведён
> inbox-watcher».

### `/loop` — это НЕ вотчер

Частая ошибка: на «взведи вотчер» хвататься за команду `/loop`. Это разные
вещи. Вотчер — фоновый shell-скрипт: **модель спит** (ноль контекста и
токенов), будит на новую задачу. `/loop` — перезапуск модели по таймеру:
**жжёт токены каждый тик** и не спит. Для inbox-push нужен вотчер, не
`/loop`.

### Известный харнесс-баг фоновых задач (эксперим. статус)

Допущение «завершение фоновой задачи будит **простаивающую** сессию И
переживает `/compact`» подтверждай вживую на конкретном окружении до
раскатки. Отдельно есть **баг самого Claude Code**: фоновые задачи (включая
`pool watch`) на некоторых версиях приходят `killed` на ближайшей границе
хода (changelog: «background tasks killed when teammate finishes a turn»
v2.1.147; «backgrounding spuriously cancelling at turn boundary» v2.1.193).
Даже если на диске лежит фикс-версия, **живая `--resume`-сессия, поднятая на
старом бинаре, держит старый код в памяти** до рестарта. Лечение — **рестарт
сессии агента** (закрыть панель → перезапустить `.bat`; `--resume` хранит
контекст). Не срочно: pull-`[POOL INBOX]` держит доставку и без вотчера.

## 2. Борд (`pool board`)

Живая доска пула — терминальный монитор для человека, замена внешнему
Task-UI. `pool board` рисует по строке на агента; `pool board -Show`
открывает её в **отдельном окне** с авто-обновлением. Базовая часть строки
(состояние ящика: `pending` / `in progress`, цветом) описана в
[Pool Communication §4](pool-communication.md) — здесь разберём **две
надстроечные колонки** и шапку.

### Колонка вотчера — `w`

Живость вотчера читается из его heartbeat-lock (`<bus>/.watch/lock-<owner>.txt`),
**read-only** (борд `.watch/` не создаёт):

| Значение | Смысл |
|----------|-------|
| `w on` | Свежий lock (моложе ~150с) — вотчер взведён и спит. |
| `w stale <age>` | Lock есть, но протух — вотчер умер/завис. |
| `w off` | Lock'а нет — вотчер не взведён (или watcherless-роль). |

Порог борда (~150с) чуть больше самопроверки вотчера (~135с) — чтобы
колонка не «мигала» на границе цикла.

### Колонка активности — `act`

Что агент делает **прямо сейчас**, из `<bus>/.activity/<owner>/` (пишет hook
`pool activity`, §3):

| Значение | Смысл |
|----------|-------|
| `act busy` | Сессия в ходе (был `UserPromptSubmit`, `Stop` ещё не пришёл). |
| `act idle` | Ход завершён (пришёл `Stop`). |
| `act sub<N>` | Идут N субагентов (N маркер-файлов `sub-*`). |
| `act busy?` | «busy», но метка старше 15 мин без `Stop` — либо очень долгий тихий ход, либо сессия умерла (различает колонка `w`). |
| `act -` | Нет данных — hook активности не заведён у этого пула. |

### Шапка борда

Две сводки сверху:

- **`N/M watchers`** — у скольких из M агентов вотчер `on` (зелёная, если у
  всех; серая, если ни у кого).
- **`N active`** — сколько агентов «активны» (`busy` / `busy?` / `sub`).

Отдельно борд считает **`working`** — более строгое «пул реально
работает»: `busy` + `sub` + `busy?`, **у которого вотчер ещё жив** (`w on`).
Смысл: долгий тихий ход (`busy?`) при живом вотчере — это работа, а не
остановка; а `busy?` с мёртвым/отсутствующим вотчером — вероятно
крашнувшаяся сессия, её в «working» не считаем. Эта величина питает
нотификатор простоя (§4).

### Борд — в своём окне

Живой борд поднимает [../scripts/board-window.ps1](../scripts/board-window.ps1)
(`pool board -Watch` в новом окне PowerShell). Использования два: (1)
wrapper **ведущего** зовёт его на старте — доска всплывает автоматически;
(2) агент или пользователь запускает on-demand (`pool board -Show` или
двойным кликом по per-pool bat). **Идемпотентно**: если живое окно борда для
**этой же** шины уже открыто, второе не поднимается (проверка по CommandLine
процесса).

> Живой борд показывает состояние **ящиков** (pending/in-progress) и живость
> сессий, а не «идёт ли работа над задачей». Картина «все агенты `idle`, а
> new/cur полны» — это **штатный затихший, но живой пул** (процессы целы,
> просто `0 active`), НЕ поломка. Уже открытое окно борда крутит старый код
> в памяти — для нового вида колонок закрыть и переоткрыть.

## 3. Hook активности — `pool activity`

Колонку `act` питает hook `pool activity` — **env-driven и полностью
молчаливый** (пишет только файлы, ничего в stdout, чтобы не засорять
контекст; обёрнут так, что не может уронить ход). Регистрируется в
`settings.local.json` пула на четыре события Claude Code, читает payload из
stdin и сам диспатчит по `hook_event_name`:

| Событие Claude Code | Действие hook'а |
|---------------------|-----------------|
| `UserPromptSubmit` | `state = busy` + подмести осиротевшие маркеры `sub-*` (TTL 2ч). |
| `Stop` | `state = idle`. |
| `SubagentStart` | Создать маркер-файл `sub-<agent_id>`. |
| `SubagentStop` | Удалить `sub-<agent_id>`. |

Состояние — два вида файлов в `<bus>/.activity/<owner>/`:
`state.json` (`{state, ts}`) для busy/idle и по одному пустому файлу
`sub-<agent_id>` на каждого живого субагента. **Файл-на-субагента (а не
общий счётчик)** — чтобы параллельные субагенты не гонялись за один
счётчик; каждый трогает свой файл. Пропущенный `SubagentStop` не «залипнет»
навсегда — осиротевшие `sub-*` подметаются на `UserPromptSubmit` по TTL.

### Эмпирика хук-событий Claude Code

Порядок и payload сняты живым прогоном (headless, версия 2.1.186). Один ход
с tool-вызовом и диспатчем субагента дал события по порядку:

```
SessionStart → UserPromptSubmit → PreToolUse/PostToolUse (главный)
  → PreToolUse[Agent] → SubagentStart
  → PreToolUse/PostToolUse +agent_id   (инструменты САМОГО субагента)
  → SubagentStop → PostToolUse[Agent]
  → Stop → SessionEnd
```

**Ключ к детекту активности** — инструменты субагента всплывают в
**родительских** `Pre/PostToolUse`, помеченные `agent_id` (+`agent_type`).
Отсюда однозначно:

- активность **главного** агента = события **без** `agent_id`;
- активность **субагента** = события **с** `agent_id`;
- число одновременных субагентов = пары `SubagentStart`→`SubagentStop`
  (= маркеры `sub-*`);
- «закончил → idle» = `Stop` (надёжно); `busy` = `UserPromptSubmit` /
  tool-события.

Полезные подтверждения этого прогона: `SubagentStart` и `SessionEnd` —
настоящие hook-события Claude Code; статус-лайн busy/idle **не** несёт (только
model/context/limits/effort/tokens), поэтому активность и берут из hook'ов, а
не из статус-лайна. Хуки наследуют env сессии → неймспейс по
`$env:AGENT_OWNER` (как у inbox-hook'а).

## 4. Нотификатор простоя (`notify-pool-idle.ps1`)

Опциональный тост «пул полностью остановился». Включается флагом
(`pool board -Watch -Notify`) или глобально **sentinel-файлом** `.board-notify`
рядом со скриптами (есть файл = включено).

Триггер — **один тост на переход `working → 0`** (весь пул встал): борд в
цикле сравнивает текущее `working` (§2) с прошлым и, если было `>0`, а стало
`0`, зовёт [../scripts/notify-pool-idle.ps1](../scripts/notify-pool-idle.ps1)
ровно один раз; перевзводится, когда работа возобновится. Сам нотификатор —
BurntToast, если модуль установлен, иначе встроенный `NotifyIcon`-balloon
(без зависимостей).

> Почему через `working`, а не `active`: долгий тихий ход (`busy?`) при
> живом вотчере в `working` **входит** — иначе пул ложно читался бы как
> «встал» посреди длинной операции. Крашнувшаяся сессия (вотчер протух) в
> `working` не входит — тост срабатывает корректно. Минорный зазор:
> watcherless-роль в состоянии `busy?` не имеет liveness-сигнала и может
> дать ложное «встал».
