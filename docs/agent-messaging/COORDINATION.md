# Координация в пуле — `pool` (maildir-шина)   ·   L1: операционный справочник

> Это **L1** — компактный рабочий минимум для агента в пуле. Полная спека (env vars, identity, lifecycle шины, hook, диагностика, тиражирование, обоснования) — **L2** `..\standards\agent-pool-communication-standard.md`. **Рабочему агенту L2 читать не нужно** — всё операционное здесь.

Координация между агентами — через ОДНУ команду `pool.ps1`, **НЕ** `TaskCreate`/`TaskUpdate`. Tasks API остаётся только под личные todo (`metadata.kind="personal"`).

Алиас в сессии: `$pool = "<workspace-root>/.launcher/pool-bus/pool.ps1"` (зовётся через `pwsh -NoProfile -File $pool ...`). Твои `owner`/`BusRoot` — в `$env:AGENT_OWNER` / `$env:POOL_BUS_ROOT` (ставит wrapper; в `inbox`/`mine`/`claim`/`ack`/`dismiss` можно не передавать — берутся из env).

## Команды

| Действие | Команда |
|---|---|
| Поставить задачу соседу | `& $pool send -To <peer> -From $env:AGENT_OWNER -Subject "<тема>" -BodyFile <путь.md>` |
| Ответить / отчитаться по задаче | `& $pool reply -To <отправитель> -From $env:AGENT_OWNER -Subject "Re: ..." -BodyFile <путь.md> -InReplyTo <id>` |
| Сообщение (не задача), тихое | `& $pool note -To <peer> -From $env:AGENT_OWNER -Subject "<тема>" -BodyFile <путь.md>` |
| Сообщение с побудкой | `& $pool note ... -Wake` |
| Входящие | баннер `[POOL INBOX]` каждый ход; вручную `& $pool inbox` |
| Моя «тарелка» (в работе + ожидают + сообщения) | `& $pool mine` |
| Взять задачу в работу | `& $pool claim -Id <id>` |
| Завершить (после ack соседа) | `& $pool ack -Id <id>` |
| Прочитал сообщение → убрать | `& $pool dismiss -Id <id>` |
| Готов к гашению (по задаче «завершение работы») | `& $pool ready` — **единственный** способ подтвердить готовность |
| Доска пула (снимок) | `& $pool board` |
| Живая доска в новом окне | `& $pool board -Show` (или двойной клик `board-<тег>.bat`; идемпотентно, авто-refresh ~8с, Ctrl+C — выход) |
| Вотчер (опц.) | `& $pool monitor` — инструментом `Monitor`, `persistent: true` |

**Задача** (`send`/`reply`) — требует действия (claim → делаешь → `ack` или `reply`), висит в `[POOL INBOX]` как `pending`, видна на борде, будит вотчер.

**`claim` — это НЕ «прочитал».** Он лишь забирает задачу себе; тело остаётся в файле, путь к нему печатается сразу после `CLAIMED`. **Открой файл и выполняй по нему, а не по памяти о прошлых похожих задачах** — инструкции меняются, память нет. На этом уже горели: 2026-07-27 лид заклеймил задачу гашения, тело не открыл, отработал по памяти и подтвердился по устаревшему пути — роль зависла в «ТАЙМАУТ».

**Готовность к гашению — только `& $pool ready`.** Куда класть флаг, знает скрипт (шина и owner берутся из env сессии). Файл руками не создавай; путь из старых задач/памяти вида `~/.claude/.control/shutdown-ready-<owner>` устарел. Команда откажет, если гашение не запущено или ты ещё не взял задачу — это защита: флаг разрешает контроллеру убить твою сессию.
**Сообщение** (`note`) — FYI, не задача: отдельная секция `[POOL NOTE]`, на борде нет, закрывается одним `dismiss` (без claim/ack). `-Wake` будит так же, как задача.

**Ответ — только когда он нужен (правило владельца, 20.08.2026).** Выполнил задачу или обработал сообщение — ответное письмо шлёшь **только если** ответ прямо запрошен ИЛИ по итогам обработки выяснилось что-то, что должно поменять действия отправителя. В ином случае — просто закрытие предусмотренным способом (`ack` по задаче, `dismiss` по сообщению), **без писем «готово / принял / спасибо»** — именно они порождают неконтролируемый вал в шине. Зеркальная обязанность постановщика: ставишь задачу и ждёшь отчёта — запроси ответ в теле ЯВНО.

Тело — в файл (`-BodyFile`, UTF-8 без BOM), а не инлайн `-Body` (cmd бьёт кириллицу).

**После перезапуска / `/compact`:** ты НЕ помнишь ни того, что взял, ни того, что знал. Два шага, в этом порядке.
**Память:** якорная запись «где я остановился» (первая строка `MEMORY.md`) и записи `task_` — оглавление приходит в контекст само, тела записей нет.
**Тарелка:** `[POOL INBOX]`/`inbox` показывают только новое (`new/`). **`pool mine`** покажет `cur/` (взятое в работу) и `new/` (ожидающее); по задаче из `cur/` прочти её файл (путь печатает `mine`), продолжи, в конце `ack`. `mine` вернёт задачи, но не знание — потому он и второй.

Борд: колонка `w` — вотчер (`on` взведён · `off` не взведён · `stale` протух), `act` — активность сейчас (`busy` · `sub<N>` крутит субагентов · `idle` ждёт · `busy?` >15м без хука). Легенда — в шапке борда; полная семантика — L2 §13. Борд висит в окне → держит старый код `pool.ps1`; после правок скрипта переоткрой окно.

## Обязательства — порог перед письмом

**Прежде чем писать соседу, назови обязательство: ЧТО требуется и по какому событию ты САМ увидишь, что дождался.** Нечего назвать — письма нет. Это правило роли, а не проверка движка.

| Действие | Как |
|---|---|
| Открыть обязательство | `& $pool send ... -Opens <ключ> -Expect "<что требуется и зачем тебе>" -CloseWhen "<по чему видно, что дождался>"` |
| Привязать письмо к открытому | `& $pool reply ... -About <ключ>` |
| Закрыть, никого не отвлекая | `& $pool close -Key <ключ> -Outcome fulfilled` (либо `-Outcome withdrawn`) |
| Поправить свою же формулировку | `& $pool amend -Key <ключ> -Expect "<новое>" -CloseWhen "<новое>"` |
| Закрыть письмом, если есть что сказать | `& $pool reply ... -Closes <ключ> -Outcome fulfilled` |

**Ключ** — латиница, цифры, дефис; уникален в пуле; придумывает открывающий.

### Два поля — два разных вопроса

**`-Expect` — что требуется по существу.** Пиши в повелительной форме: «Требуется <что должно появиться или быть решено> — <зачем это тебе>». «Требуется пилот такой-то роли» — отписка: это пересказ темы письма, а не предмет.

**`-CloseWhen` — по какому событию ты увидишь, что дождался.** Признак обязан читаться ОТДЕЛЬНО от письма: через час ты встретишь его в своде `mine`, где рядом не будет ни темы, ни текста. Поэтому называй предмет своим именем, а не «он» и «оба документа».

🛑 **Признак проверяешь ТЫ, а не исполнитель.** «Исполнитель объявил, что закончил» признаком не является: так проверять нечего. И **переадресация вопроса выше** («вернусь, когда мне ответят») тоже не закрывает — если ждёшь решения, пиши в признак, ЧТО должно быть в ответе.

🛑 **Признак описывает предмет, а не приёмку.** «Заказчик ответил „принимаю"» писать нельзя — приёмка и есть закрытие, вышло бы «закрыто, когда я закрыл».

**Состав признака.** Ждёшь вещь — назови три вещи: предмет, где он появится, по чему видно, что это всё, а не часть (число, полнота, перечень). Ждёшь решение — назови предмет и перечень допустимых ответов.

### Образцы

Ждёшь вещь:
```
-Opens korpus-utverzhdenij
-Expect "корпус утверждений из памяти оператора — вход для встречной проверки поведением, без него сверять нечего"
-CloseWhen "корпус утверждений памяти оператора прислан, в нём названо число прочитанных записей из 136, у каждого утверждения указан путь к источнику"
```

Ждёшь решение:
```
-Opens sostav-snimka
-Expect "решение по рабочей зоне оператора, которой нет в снимке — от него зависит, проверяемы ли 59 записей памяти из 136"
-CloseWhen "пришёл ответ, в котором названо, что делать с отсутствующей зоной: исключена намеренно, дать листинг или доснять в снимок"
```

### Кто закрывает

**Закрывает тот, кто ждал** — он же и проверяет признак. Исполнитель сдаёт работу письмом с `-About`, а закрытие ставит ждущий: `& $pool reply ... -Closes <ключ> -Outcome fulfilled`.

**Закрывай командой `close`, а не письмом.** Она кладёт событие в архив шины: обязательство исчезает из свода у обеих сторон, и ничей ход на это не тратится. Письмом закрывай только тогда, когда к закрытию есть что сказать по существу — замечание, поправка, следующий шаг.

**Формулировку своего обязательства правит тот, кто его открыл** — командой `amend`. Ошибся в числе, назвал не тот файл, изменились условия — поправь, а не заводи новый ключ. Чужой ключ править нельзя: условие приёмки принадлежит тому, кто принимает; правка от постороннего не применится и попадёт в разбор.

⚠️ **Принять работу с иными числами можно и без правки.** Если исполнитель показал, что в признаке ошибка — в рамке стояло «из 71 письма», а их 68, — достаточно согласиться в переписке и закрыть. `amend` нужен там, где формулировка живёт дальше и её увидит третий: свод показывает исходный текст, а не вашу договорённость.

🛑 **Закрытый ключ работу не принимает.** Пришло исправление после закрытия — оно видно в разборе отдельной строкой, а не теряется среди кривых ключей. Слать такое надо: молчать хуже. Но если работа продолжается, значит ключ закрыт преждевременно.

### Что ещё ты увидишь в своём своде

**Секция «obligations in OTHER pools».** Обязательства, которые ты открыл соседу из ДРУГОГО пула,
живут в его шине, а не в твоей. Свод показывает их отдельной секцией, с именем пула. Закрывать
их надо там же, где открыл, — указав шину соседа: `& $pool close -Key <ключ> -BusRoot <его шина>`.
Секции нет — значит таких обязательств нет.

⚠️ Письмо в чужой пул само называет твой: движок добавляет в шапку строку `FromPool`. От тебя
ничего не требуется, вводить её руками не надо.

**Письма от `pool-monitor` про форму.** Обходчик читает шапки и пишет автору, если ссылки не
сходятся: ключ не по форме, привязка к несуществующему или закрытому обязательству, закрытие
неоткрытого, забытый исход, правка не от открывшего. Это заметка, отвечать не нужно — надо
поправить в следующем письме.

🛑 **Он проверяет только связность, а не смысл.** Отписку от настоящего ожидания машина не
отличит, непроверяемый признак не заметит. Качество формулировок разбирает ведущий пула.

### Когда пометки нет

**Письмо без пометки бывает у двоих: у обвязки (окрик антифлуда, команды контроллера) и у рассылки правил.** Всё остальное либо открывает ожидание (`-Opens`), либо ссылается на уже открытое (`-About`). Это касается и писем, которые кажутся самостоятельными:

- **согласование метода** — как считаем, что берём за единицу — идёт `-About` того обязательства, ради которого считаем;
- **находка к сведению** — «механизм не воспроизвёлся» — идёт `-About` того, из которого она добыта;
- **разбор по итогам** — `-About` разбираемого.

Отдельное обязательство на одностороннее уведомление не заводи: у него нет ждущего, а обязательство без ждущего — запись без хозяина.

**Ждёшь решение, которое сосед сам принять не может?** Признак «сосед ответил» тут негоден: он наступит, когда сосед передаст вопрос выше, а решения всё ещё не будет. Пиши в признак САМО решение — что должно быть в ответе.

**Длина переписки сама по себе не порок.** Замер живого прогона: из пятнадцати писем сверх минимума тринадцать чинили основание — часовые пояса в датах, ошибку счёта при выдаче задания, находку, опровергшую принятый вывод. Про объём работы не спорило ни одно, а деление такого треда надвое дало бы писем БОЛЬШЕ. Смотри не на длину, а на то, **что именно чинят письма**: много про предмет — нормально, много про основание — сигнал, что основание надо было проверить раньше.

🛑 **Единицы счёта выясняются ДО раздачи задания.** На том же прогоне первая волна стоила 17 писем, вторая — 10 при том же объёме работы: к её началу пояса времени и способ счёта были уже выяснены. Ставишь в признак число — убедись, что оно посчитано тем же способом, каким его проверит исполнитель.

**Два исхода, и это не одно и то же:** `fulfilled` — сделано; `withdrawn` — отпало, снято за ненадобностью. Молчание исходом не считается.

**Ответ внутри открытого обязательства и письмо о закрытии** нового ключа не заводят — они несут `-About` или `-Closes` соответственно.

**Что видишь ты:** `pool mine` печатает твои открытые обязательства — и открытые тобой, и открытые на тебя. При подъёме и после сжатия контекста назови по каждому исход: «ещё жду», «исполнено», «снято».

**Что делает движок: ничего.** Кривой ключ, ссылка на несуществующий, забытый исход — письмо всё равно уходит; ошибку замечает обходчик постфактум. Имена ключей пиши полностью: `-Close` неоднозначно (`-CloseWhen` / `-Closes`), `-O` неоднозначно (`-Owner` / `-Opens` / `-Outcome`).

⚠️ Значение `-CloseWhen` перед записью санитизируется: вертикальная черта экранируется, перевод строки схлопывается в пробел — иначе разъедется таблица шапки. При чтении текст восстанавливается.

## Вотчер — его держит общая вахта, а не ты

🛑 **Личных сторожей на сервере нет — взводить их не надо.** За все пулы держит вахту один общий процесс (`shop-watch.py --all`): он будит роль, когда ей приходит задача. Семь личных сторожей по 170 МиБ заменены одним на 13, поэтому «свой» тут не улучшение, а лишний процесс поверх работающего.

⚠️ Если Stop-гейт в конце хода всё-таки требует взвести сторожа — это не спор приказов, а сообщение о поломке: общая вахта не подтвердилась. Взводи, как он просит, и напиши об этом супервайзору сервера (`pool send`). Чинить вахту — его дело; процессы и замки самой искать не нужно. Команда на этот случай — инструмент **`Monitor` с `persistent: true`**:
```
pwsh -NoProfile -File <workspace-root>/.launcher/pool-bus/pool.ps1 monitor
```

Что про вахту нужно знать, чтобы работать:

- **Пришла задача — первым делом `claim`.** Это единственный способ сказать вахте «взял»: заклеймленная задача уходит из `new/` в твой `cur/`, и будить по ней перестают. Не заклеймишь — разбудит снова, но не чаще раза в 15 минут.
- **Заметка-побудка (`note -Wake`) одноразовая:** её id запоминает леджер, второй раз она не придёт. Задача — наоборот, будит, пока лежит в `new/`.
- **Пока ты ждёшь, модель выключена** — ожидание не стоит ни хода, ни контекста.
- **Баннер `[POOL INBOX]`** приходит сам в начале хода и страхует промахи вахты: даже если разбудить не смогли, входящие ты увидишь.

## Инварианты (держит инструмент, не твоя память)

- Сообщение = один файл; адрес получателя = ПАПКА → «двух половин» (payload без задачи) не бывает, `send` доставляет целиком.
- Отчёт = `reply` (свежий id) → у постановщика срабатывают и POOL INBOX, и вотчер. **Не закрывай чужую задачу** как способ «отчитаться».
- id уникальны и НИКОГДА не переиспользуются. `claim` атомарен: первый забрал — остальным «уже взято».
- Личные todo, бэклог (`00_docs/backlog.md`), per-owner память (`.memory/<owner>/`), git-история, зоны записи — как раньше (см. свой `_agent_pool_setup-*.md` + `agent-pool-zones.md`).
