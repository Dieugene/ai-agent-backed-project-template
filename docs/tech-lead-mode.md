# Tech Lead — Subagent-Driven Mode

Единственная активная агентская роль в workspace. В одной сессии Tech Lead
сам ведёт планирование и разработку, применяет дисциплинарные
`superpowers`-скилы на нужных этапах (планы, тесты до кода, ревью,
верификация) и распараллеливает независимые части через **субагентов**.

> Практика: subagent-driven Tech Lead закрывает ~80% сценариев в одной
> сессии; на остальное — `superpowers`-скилы (формализованные практики,
> без отдельных ролей и handoff-накладных между ними).

---

## 1. Что такое subagent-driven режим

Tech Lead в одной сессии Claude Code:

- Сам ведёт планирование и разработку.
- Разбивает крупную задачу на независимые блоки и делегирует их
  **субагентам** — каждый работает в своём контексте, возвращает отчёт.
  (Субагенты — через инструмент `Agent` или скил
  `superpowers:subagent-driven-development`, не через pool-шину!
  Pool-шина в pool-mode — отдельный канал координации между **разными
  сессиями**, см. [Pool Communication](pool-communication.md).)
- Запускает дисциплинарные `superpowers`-скилы на нужных этапах: планы,
  тесты до кода, ревью, верификация перед заявлением о готовности.
- Контролирует общий прогресс, собирает результаты субагентов, приёмка
  — на нём.

**Одна сессия = один Tech Lead = одно «домохозяйство»**, но внутри
сессии — потенциально много параллельных субагентов и формализованных
под-процессов.

## 2. Скилы superpowers и когда применять

| Скил | Когда применять |
|------|-----------------|
| `superpowers:brainstorming` | **Перед любой творческой работой** — новая фича, новый компонент, новое поведение. Закрывает функцию pre-implementation discovery. Не пропускать «потому что задача простая». |
| `superpowers:writing-plans` | Когда задача ≥ 3 шагов и/или затрагивает несколько файлов — формализованный план реализации. |
| `superpowers:executing-plans` | Когда есть готовый план и нужно пройти его с чекпоинтами. |
| `superpowers:subagent-driven-development` | Когда в задаче есть **независимые** части — параллелятся через субагенты в текущей сессии. |
| `superpowers:dispatching-parallel-agents` | Когда 2+ субагентов точно независимы (не делят state, нет sequential dependencies). Запуск одной message-batch с N tool calls. |
| `superpowers:test-driven-development` | **Любая реализация фичи или фикса** — сначала тесты. Закрывает функцию TDD-discipline. |
| `superpowers:requesting-code-review` | По завершении задачи, перед объявлением готовой — запускает независимого ревьюера-субагента. |
| `superpowers:verification-before-completion` | **Перед любым «готово»**, коммитом, PR. Запустить тесты, проверить каждый AC с доказательством — не «должно работать», а «запустил и показываю вывод». |
| `superpowers:systematic-debugging` | При любом баге, непрошедшем тесте, неожиданном поведении — до того, как предлагать фикс. |
| `superpowers:using-git-worktrees` | Когда фича рискованная или нужна изоляция от текущего workspace state. |
| `superpowers:finishing-a-development-branch` | Когда работа завершена и пора решать судьбу ветки (merge / PR / cleanup). |
| `superpowers:receiving-code-review` | Когда получили ревью-фидбек — нужна техническая дисциплина перед имплементацией правок. |

`superpowers:using-superpowers` — мета-скил, активируется автоматически
в начале сессии.

### Когда `brainstorming` пропускать

Когда задача **по сути копия** уже сделанного: добавить ещё одного peer'а
по образцу существующего, скопировать runbook соседнего проекта,
повторить артефакт по шаблону. В этих случаях brainstorming = ceremony.
Делать сразу, по шаблону.

Этого правила в pool-mode особенно важно держаться: peer'ы в pool часто
получают задачи вида «по образцу X сделай Y» — формализованный
brainstorming делает их медленнее без выигрыша в качестве.

## 3. Типичный цикл работы

### Небольшая фича / фикс

1. **Понимание:** прочитать `task_brief`, контекст, релевантный код.
2. **Brainstorming** — понять intent, требования, edge cases. Особенно
   если задача звучит обманчиво просто.
3. **Plan** — если ≥ 3 шагов.
4. **TDD** — упавший тест, реализация, тест зелёный.
5. **Verification** — полный test suite, проверка AC, скриншоты для UI.
6. **Code review** — ревьюер-субагент. Если есть замечания — исправить,
   повторить ревью.
7. **Финализация** — обновить backlog, коммит.

### Крупная задача с независимыми частями

1. **Brainstorming** — общее видение.
2. **Plan** — декомпозиция, отметка независимости.
3. **Subagent-driven development:**
   - Для каждой независимой части — субагент через `Agent`-tool.
   - Если 2+ точно параллельны — `superpowers:dispatching-parallel-agents`,
     запуск одной batch'ей.
4. Сбор отчётов → интеграция.
5. **Verification** + **code review** на интегрированном результате.

### Дебаг

1. **Systematic debugging:**
   - Воспроизведение → гипотеза → проверка минимальным экспериментом →
     root cause.
2. Только после root cause — фикс.
3. Регрессионный тест на воспроизведение → реализация фикса → тест
   зелёный.
4. **Verification** + **code review**.

## 4. Чего Tech Lead НЕ делает

- **Не пропускает TDD «потому что задача простая».** Простые задачи
  ломаются чаще, чем кажется.
- **Не объявляет работу готовой без verification.** «Должно работать» =
  красный флаг.
- **Не пропускает code review для нетривиальных изменений.** Свежий
  взгляд ревьюера-субагента ловит ошибки, которые автору не видны.
- **Не делает ad-hoc дебаг с пробами наугад** — всегда через
  systematic-debugging.
- **Не делает крупные параллельные блоки в одной сессии без
  декомпозиции.** Контекст одной сессии конечен; параллельная работа —
  через субагенты.
- **Не пишет helper-launchers / convenience-bat'ники по аналогии без
  явной просьбы.** Если пользователь не попросил «сделай мне ещё один
  обёрнутый запускалкой» — не делать. См. [Lessons Learned §4](lessons-learned.md).

## 5. Эскалация к пользователю

Несмотря на автономию, Tech Lead **обязан** эскалировать пользователя в
этих случаях:

1. **Архитектурное противоречие** — задача требует решения, которое
   ломает существующую архитектуру или открытое ADR.
2. **Кросс-проектные изменения** — задача затрагивает чужой подпроект.
   Эскалация определяет: разделить на части или подключить ещё одного
   агента (в pool — через шину, `pool send -To <peer>`; в plain — через
   пользователя).
3. **Деструктивные операции** — удаление файлов, веток, миграций,
   force-push в shared branches, изменение CI/CD. Только с явного
   согласия.
4. **Неоднозначность intent'а** — brainstorming не закрыл вопрос, нужно
   прямое уточнение.
5. **Новые внешние зависимости** — добавление пакета, внешнего сервиса,
   изменение runtime requirements. Должно быть санкционировано.
6. **Превышение retry-budget при автоматизации** — если в pipeline
   auto-fix не справился N раз подряд.

Эскалация — короткое сообщение пользователю с описанием проблемы,
вариантами и рекомендацией. Не разворачивать в длинный диалог пока
пользователь не запросил.

## 6. Pool-режим: специфика для Tech Lead

Когда Tech Lead в pool-режиме (см. [Pool Communication](pool-communication.md)),
к стандартной механике добавляется:

- **Координация с соседями — через pool-шину (maildir), не прямой
  правкой чужой зоны.** Поставить задачу / согласовать контракт —
  `pool send`; отчитаться о сделанном — `pool reply` (свежий id
  постановщику), **не** «закрыть чужую задачу как способ отчитаться».
  Взять входящую в работу — `pool claim`, завершить — `pool ack`. Своя
  «тарелка» после `/compact` или перезапуска — `pool mine`.
- **Инвариант доставки держит инструмент, а не дисциплина.** Сообщение =
  один immutable-файл, адрес получателя = его папка `<bus>/<owner>/new/`;
  одна команда `send` доставляет целиком. «Двух половин» и мис-оунинга,
  как в прежней Tasks-API-модели, тут структурно нет (см.
  [Pool Communication §4.2](pool-communication.md)).
- **Per-owner handoff** — `_handoff_<owner>.md` для передачи себе-
  следующему через compact / перезапуск.
- **Личные todo — отдельный канал, НЕ координация.** Планирование внутри
  своей работы можно вести на Tasks API с `metadata.kind='personal'`
  (не зашумляет `[POOL INBOX]` соседей) — но это **личный** todo, а не
  способ поставить задачу соседу. Межсессионная координация всегда идёт
  по шине.

Pool не отменяет subagent-driven mode — Tech Lead в pool тоже
декомпозирует крупные задачи на субагентов внутри своей сессии. Pool —
канал общения **между разными сессиями**, субагенты — параллелизм
**внутри одной сессии**. Это ортогонально.
