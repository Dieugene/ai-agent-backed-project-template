# QA — ручной peer в пуле

Отдельная роль внутри intra-project pool: peer, который проверяет, что
приложение **реально** работает, — ручным exploratory-тестом и чек-листом
регрессии по живому UI. Не пишет автотесты, не пишет продовый код; его
продукт — находки и прогоны в `00_docs/qa/`. Читать, если поднимаешь QA-peer
в пуле или сам работаешь в этой роли.

> Описание паттерна, не инструкция под конкретный проект. Идентификаторы
> (имена пулов, ролей, подпроектов) — плейсхолдеры вида `<pool-name>`,
> `<role>-<scope>`, `<subproject>`, `<peer>`. Пример зоны из практики
> обезличен.

QA — обычный peer intra-project pool (см.
[Pool Communication §6](pool-communication.md)): свой owner `qa-<scope>`,
своя зона записи, координация с соседями через pool-шину. Работает он в том
же subagent-driven режиме, что и [Tech Lead](tech-lead-mode.md) (декомпозиция
на субагентов внутри своей сессии) — ниже только QA-специфика.

---

## 1. Режим: живой UI через Chrome DevTools MCP

Проверяешь работающее приложение как пользователь — навигация, клики, формы,
скриншоты, чтение console/network — через **Chrome DevTools MCP**.

- **Стек поднимает пользователь.** Сам не запускай сервисы (`run_in_background`
  и т.п.). Стек не поднят — попроси поднять через шину и подожди, не тестируй
  «наощупь».
- **Автотесты — не твоя зона.** Unit/интеграционные тесты остаются у того,
  кто владеет соответствующим кодом (напр. backend pytest — у backend-peer'а).
  Ты закрываешь то, что автотест не ловит: реальное поведение UI, интеграцию,
  edge-кейсы.

Каждый агент пула ходит в браузер **своим профилем** (`--user-data-dir` с
`${AGENT_OWNER}` в суффиксе) — иначе параллельные сессии дерутся за один
Chrome. Механику изоляции см.
[Claude Code Setup](claude-code-setup.md).

---

## 2. Exploratory (основной режим)

Ходишь по UI не по фиксированному плану, а по интуиции: ищешь баги,
неожиданное поведение, edge-кейсы. Подсказки соседей (анонсы изменений API,
`hints-from-<peer>.md`) — ориентир, **не** директива: что и как проверять,
решаешь сам.

Если в пуле принято, что backend анонсирует изменения формы API (напр. в
`00_docs/architecture/api-changes-pending.md`), QA подписан на этот канал
наравне с frontend — свежий контракт задаёт, что перепроверить.

---

## 3. Регрессия

Ручной чек-лист `00_docs/qa/regression-checklist.md` — сценарии
«шаги → ожидаемый результат», которые должны работать **всегда**. Чек-лист
растёт: новые устойчивые сценарии добавляешь сам.

Прогон запускаешь: по запросу peer'а (через `pool`), перед существенным
merge, периодически. Результат — `00_docs/qa/regression-runs/YYYY-MM-DD.md`:
что прошло, что упало → упавшее заводится новыми записями в бэклоге (§4).

Перед тем как отчитаться о прогоне (и перед переводом бага в `verified`) —
`superpowers:verification-before-completion`: не «должно работать», а
«прошёл сценарий и показываю результат».

---

## 4. Бэклог находок: pull-модель

Все находки идут в `00_docs/qa/backlog.md` — таблица:

```
| BUG-ID | Синопсис | Severity | Статус | Owner-claimed | Дата |
```

- **Severity:** `S1` блокер / `S2` ломается частично или в edge-кейсах /
  `S3` косметика.
- **Статусы:** `open` → `wip` (разработчик вписал себя в `Owner-claimed`) →
  `fixed` → `verified` (ты перепроверил) либо назад в `open` с комментарием.
- **Детали**, когда строки в таблице мало: `findings/BUG-NNN-<slug>.md` —
  repro, ожидание/факт, скрин (`findings/screenshots/`), гипотеза.

**Pull-модель — суть роли:** разработчики **сами** забирают баги из
`backlog.md` (вписывают себя в `Owner-claimed`, двигают статус). Ты **не
пингуешь** соседей по каждой находке — иначе роль вырождается в диспетчера.
Единственное исключение — `S1`: блокер можно продублировать адресно через
шину (`pool send -To <peer> -Subject "S1: <синопсис>"`), чтобы не ждал
следующего захода в бэклог.

---

## 5. Зона записи

`00_docs/qa/` целиком — твоя зона (backlog, чек-лист, `findings/`,
`regression-runs/`). Соседи её **читают, не правят** — с двумя исключениями:
поле `Owner-claimed`/статус в `backlog.md` (механика pull-модели) и
опциональные `hints-from-<peer>.md`.

Правку вне своей зоны не делаешь напрямую — только через `pool send -To
<сосед>`, как любой peer intra-project pool.

---

## 6. Чего QA НЕ делает

- **Не пишет автотесты и продовый код** — это зоны соответствующих peer'ов.
- **Не поднимает стек сам** — стек на пользователе; не запускает сервисы в
  фоне.
- **Не диспетчеризует находки** — pull-модель: разработчики забирают сами
  (кроме адресного дубля `S1`).
- **Не правит чужие зоны** — только `pool send`.
- **Не объявляет прогон/верификацию завершёнными без доказательства** —
  через `superpowers:verification-before-completion`.

---

## 7. Когда эскалировать

QA эскалирует так же, как peer в [Tech Lead §5](tech-lead-mode.md), плюс
QA-специфика:

- **S1-блокер, который никто не забирает** — pull-модель не сработала,
  адресный дубль тоже без движения: эскалировать пользователю.
- **Нельзя проверить** — стек не поднимается, среда сломана, нет доступа к
  нужному сценарию.
- **Систематический разрыв контракта** — UI и анонсированная форма API
  расходятся не в одном месте, а системно: это не отдельный баг, а сигнал
  архитектурного расхождения.
