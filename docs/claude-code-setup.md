# Claude Code — настройка среды под workspace

Как настроить сам инструмент Claude Code под workspace, где живут
**постоянные именованные сессии** и **пулы агентов**: усилие модели
(effort), статус-лайн, режим постоянных сессий, изоляция браузера между
агентами и файловая система памяти (memory).

> Аудитория — инженер, поднимающий такое пространство с нуля на Windows.
> Всё — про глобальные/пользовательские настройки Claude Code, не про код
> проекта. Пути и имена обезличены плейсхолдерами (`<workspace-root>`,
> `<user>`, `<ProjectKey>`, `<role>`, `<SessionName>`, `<pool-name>`).
> Родственные документы: [Wrapper and Hook Scripts](wrapper-and-hook-scripts.md)
> (рабочие примеры wrapper'ов), [Pool Communication](pool-communication.md)
> (координация сессий), [Workspace Organization](workspace-organization.md)
> (общая структура).

## 1. Effort-уровни и их персистентность

`/effort <level>` меняет усилие модели. Ключевая тонкость: **записывается
ли выбор на диск — зависит от уровня.**

| Уровень | Что делает `/effort` | Область действия |
|---------|----------------------|------------------|
| `low` / `medium` / `high` / `xhigh` | Пишется в `~/.claude/settings.json` (user-global, ключ `effortLevel`) | Влияет на **все последующие** сессии |
| `max` / `ultracode` | **Session-only** — в settings.json НЕ пишется | Только текущая сессия |

Файл настроек `max`/`ultracode` вообще не принимает: максимум, который
можно положить в `effortLevel`, — `xhigh`.

**Сделать `max` «липким» на несколько сессий** можно только через
env-переменную в лаунчере (`.bat`):

```bat
set CLAUDE_CODE_EFFORT_LEVEL=max
```

Она процессная: накрывает свой запуск и его субагентов, общий файл настроек
не трогает; принимает `low`/`medium`/`high`/`xhigh`/`max`/`auto`.

### Приоритет источников (высший → низший)

1. `CLAUDE_CODE_EFFORT_LEVEL` (env) —
2. флаг `--effort <level>` —
3. frontmatter активного скилла/субагента —
4. `.claude/settings.local.json` (проектный, gitignored) —
5. `.claude/settings.json` (проектный) —
6. `~/.claude/settings.json` (user-global) —
7. дефолт модели (у актуальных Opus/Sonnet/Fable — обычно `high`; у
   отдельных версий — `xhigh`).

### Практика: глобально `high`, лидеры пулов на `xhigh`

Рабочая раскладка: **глобальный `~/.claude/settings.json` — `high`**
(дефолт для всех обычных сессий), а **лидеры пулов подняты на `xhigh`
через флаг `--effort`**, не через env.

Почему флаг, а не env:

- Флаг задаёт уровень **сессии** и НЕ пишется в settings.json (в отличие
  от `/effort`), поэтому не «протекает» глобально.
- `CLAUDE_CODE_EFFORT_LEVEL` наследуется дочерними процессами, т.е. накрыл
  бы и субагентов лидера — а их обычно хотят держать на дефолте.

Механика прокидки: wrapper зовёт не `claude` напрямую, а цепочку
`.bat → pool-launch helper → claude.exe`. Поэтому в launch-helper
добавляется необязательный параметр `-Effort` и splat флага во все вызовы
`claude`, а в `.bat` лидера дописывается ` -Effort xhigh`:

```powershell
# внутри pool-launch helper
param([string]$Effort = '')
$effortArgs = if ($Effort) { @('--effort', $Effort) } else { @() }
& claude @effortArgs --resume $SessionName --dangerously-skip-permissions
```

Executors (обычные peer'ы) зовут тот же helper **без** `-Effort` → флага
нет → наследуют глобальный `high`. Смена уровня вступает в силу при
**рестарте** сессии (флаг читается на старте). Обёртки-цепочки и helper —
[Wrapper and Hook Scripts](wrapper-and-hook-scripts.md).

## 2. Статус-лайн

Статус-лайн (модель + effort, окно лимитов с reset, заполнение контекста,
токены) подключается **глобально для всех сессий машины** через ключ
`statusLine` в `~/.claude/settings.json`. Команда указывает на bash-скрипт,
рендерящий строку через `jq`:

```json
{
  "statusLine": {
    "type": "command",
    "command": "\"C:\\Program Files\\Git\\usr\\bin\\bash.exe\" /c/Users/<user>/.claude/statusline-command.sh"
  }
}
```

### Windows-нюансы (иначе строка окажется пустой)

- **Абсолютный путь к `bash.exe`** — bash не на системном PATH, поэтому
  вызывается по полному пути; путь к скрипту — в MSYS-форме
  (`/c/Users/<user>/...`).
- **Внутри скрипта — экспорт PATH.** Claude Code запускает команду не из
  bash-процесса, поэтому coreutils (`cat`/`sed`/`date`) и `jq` не находятся
  автоматически. Первой строкой скрипта:

  ```bash
  export PATH="/usr/bin:/bin:$HOME/bin:$PATH"
  ```

  (`jq` обычно кладут в `~/bin`.) Без этой строки скрипт молча падает и
  **статус-лайн пустой** — это самая частая ошибка настройки.
- **Скрипт без BOM и без CR** (LF-концы), иначе bash спотыкается.
- **settings.json правь текстовой вставкой**, не пере-сериализацией
  (`ConvertTo-Json` ломает вложенность существующих ключей).

Состав сегментов меняется правкой самого скрипта; строка перечитывается
на старте сессии (применяется в новой/перезапущенной).

## 3. Постоянные именованные сессии

Модель работы — **постоянные сессии с compaction**, а не одноразовые:
контекст сжимается через `/compact`, но сама сессия **живёт между
запусками** wrapper'а, не обнуляется. Каждая роль — именованная сессия
(`Launcher`, `DevOps`, `TechLead-<scope>`, …).

Стандарт wrapper'а plain-роли (Launcher, оркестратор и аналоги):

```bat
set AGENT_OWNER=<role>
cd /d <workspace-root>
claude --dangerously-skip-permissions --resume <SessionName>
```

- `--resume <SessionName>` — picker фильтруется по имени, пользователь
  подтверждает свою сессию (а не стартует новую с нуля).
- Имя задаётся `-n <SessionName>` (`--name`) при **первом** запуске и
  сохраняется на всех последующих resume.
- `--dangerously-skip-permissions` — bypass permission-промптов (роль
  доверенная, крутится под постоянным владельцем).

**Грабля, ради которой это всё:** голый `claude` без `--resume` стартует
**новую** сессию каждый запуск → контекст и наработки роли теряются. Wrapper
обязан resume-ить по имени.

### Env для pool-агентов

Wrapper pool-агента дополнительно выставляет переменные идентичности —
**обязательные**, без них агент вырождается в обычную независимую сессию:

- `AGENT_OWNER` — кто я (адрес в шине, фильтр inbox-баннера);
- `POOL_BUS_ROOT` — корень pool-шины;
- `CLAUDE_CODE_TASK_LIST_ID` — под **личные** todo агента.

Детали — [Pool Communication](pool-communication.md) и
[Wrapper and Hook Scripts](wrapper-and-hook-scripts.md).

### Замена сбоящей сессии

Непрерывность держит **handoff-файл роли**, а не история конкретной
сессии. Если именованная сессия начала регулярно падать (типичная
причина — баг `400 thinking blocks cannot be modified`), лечится так:
завести чистую сессию под **новым** именем (`-n <SessionName>-2`, отдельное
имя — чтобы в picker'е не путалась со сбоящей) той же роли (тот же
`AGENT_OWNER` → тот же routing → тот же handoff), старую удалить через
`/resume` picker.

## 4. Изоляция браузера между агентами

**Проблема.** Если несколько pool-агентов одновременно пользуются браузером
через MCP `chrome-devtools`, они закрывают Chrome друг другу.

**Корень.** `chrome-devtools`, подключённый в **user-scope** (top-level
`mcpServers` в `~/.claude.json`) как `npx chrome-devtools-mcp@latest`
**без** `--user-data-dir`, берёт фиксированный общий профиль
(`$HOME/.cache/chrome-devtools-mcp/chrome-profile`). Все сессии лезут в один
профиль; второй инстанс падает: `The browser is already running for <dir>.
Use --isolated` — это и есть драка/эвикция.

**Решение.** Положить в корень workspace project-scope `.mcp.json`, который
переопределяет `chrome-devtools` **только для сессий этого workspace**,
раздавая каждому агенту свой профиль по имени:

```json
{ "mcpServers": { "chrome-devtools": {
  "type": "stdio",
  "command": "npx",
  "args": ["chrome-devtools-mcp@latest",
           "--user-data-dir=<workspace-root>\\.chrome-profiles\\${AGENT_OWNER:-_plain}"],
  "env": {}
} } }
```

Каждый агент (по своему `AGENT_OWNER`) получает отдельный профиль → работают
параллельно, персистентный логин держится per-profile. Каталог
`<workspace-root>\.chrome-profiles\` создать заранее.

### Почему именно так (проверенные факты Claude Code)

- **Env-интерполяция `${VAR}` / `${VAR:-default}` работает ТОЛЬКО в
  project `.mcp.json`** — не в user-scope `~/.claude.json`. Поэтому профиль
  параметризуется именно здесь.
- **Scope MCP: Local > Project > User.** При совпадении имени берётся ОДНА
  дефиниция из высшего scope **целиком** (поля не мерджатся) → project
  `.mcp.json` чисто перекрывает глобальный `chrome-devtools`.
- **`--isolated` не подходит** — это временный профиль (теряется логин).
  Нужен именно `--user-data-dir=<path>` (постоянный per-agent профиль).
- Вступает в силу на **рестарте** каждого агента (MCP читается на старте).
  Non-browser агенты Chrome не поднимают (запуск ленивый — на первом
  browser-тул-колле), поэтому «кто пользуется браузером» указывать не нужно.
- Edge: ключ изоляции — `AGENT_OWNER`; если два разных workspace с
  одинаково-бедным owner (`tech-lead`/`dev`) браузерят одновременно, они
  поделят профиль. Риск низкий; фикс — сделать ключом «пул + owner».

## 5. Файловая система памяти (memory)

Кросс-сессионная память Claude Code — это **каталог `.md`-файлов**, не одна
монолитная заметка.

### Где лежит и как привязана к workspace

```
~/.claude/projects/<ProjectKey>/memory/
├── MEMORY.md                 # индекс, грузится в контекст каждой сессии
├── user_profile.md           # один факт = один файл
├── feedback_<...>.md
├── project_<...>.md
└── reference_<...>.md
```

- **`<ProjectKey>` определяется cwd.** Claude Code выводит его как slug
  абсолютного пути рабочей папки (диск и разделители → дефисы). Для
  workspace в `<workspace-root>` это стабильный slug этого пути. Следствие:
  **cwd роли определяет её набор памяти** — сменил cwd на другую папку →
  другой `<ProjectKey>` → другая память. Роли с общим корнем делят одну
  память; поэтому cwd в wrapper'е стоит держать стабильным.
- **`MEMORY.md` — индекс.** Одна строка-ссылка на факт, грузится в контекст
  автоматически в начале каждой сессии. Формат строки:

  ```markdown
  - [<короткий заголовок>](<file>.md) — <одна строка сути>
  ```

  Модель по индексу решает, какой факт открыть целиком.

### Один факт = один файл с frontmatter

Каждый факт — отдельный `.md`. Frontmatter несёт метаданные для рекола:

```markdown
---
name: <короткий-идентификатор>
description: <фраза для рекола: по ней модель понимает, стоит ли открывать факт>
type: reference    # user | feedback | project | reference
---

<тело: сам факт, компактно>
```

Типы:

| `type` | Что хранит |
|--------|------------|
| `user` | Стабильный профиль/предпочтения владельца |
| `feedback` | «Так делать / так не делать» — выводы из обратной связи |
| `project` | Состояние конкретного проекта/пула |
| `reference` | Переиспользуемый технический факт или рецепт |

Связи между фактами — через `[[имя-факта]]` (wiki-style), чтобы модель
подтягивала смежное.

### Правило гигиены

Память — **факт + ссылка, коротко**. Не дублировать то, что уже живёт в
коде, репозитории или `CLAUDE.md`. Длинные процедуры → в runbook'и, в
память — только якорь (что это и где лежит). Раздутая память зашумляет
контекст каждой сессии, потому что `MEMORY.md` грузится всегда.
