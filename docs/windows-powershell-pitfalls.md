# Windows / PowerShell Pitfalls

Ловушки, которые ломают работу Claude Code именно на **Windows с русской
локалью, PowerShell 5.1 и антивирусом**. Каждая проявляется не сразу и уводит
диагностику в сторону: mojibake в скриптах, «внезапно всё падает на запуске
процесса», «поиск не находит то, что точно есть», «фильтр вернул всё вместо
двух файлов». Читать до того, как правишь `.ps1`/`.bat`, гоняешь полный аудит
по репозиторию, удаляешь что-нибудь пачкой или упёрся в необъяснимый сбой
запуска.

> Плейсхолдеры: `<workspace-root>` — корень workspace; `<user-home>` /
> `$env:USERPROFILE` — домашняя папка; `<user>` — имя пользователя ОС.
> Примеры из практики обезличены.

Формат каждого раздела: **симптом → причина → рецепт**.

---

## 1. Кириллица в `.ps1`: нужен UTF-8 **с BOM**

**Симптом.** После правки `.ps1` кириллица превращается в мусор
(`Р­С‚РѕС‚...`), скрипт перестаёт парситься и падает ещё до первой строки
логики.

**Причина.** Windows PowerShell 5.1 на ru-RU локали, встретив `.ps1` **без
BOM**, читает его в системной кодовой странице (cp1251), а не UTF-8. Файл,
физически лежащий в UTF-8, интерпретируется как cp1251 → каждый кириллический
символ разваливается на пару «латиница + типографика». BOM (`EF BB BF` в начале
файла) — это явный маркер «я UTF-8», который снимает неоднозначность: с ним
PowerShell 5.1 читает файл правильно.

Отсюда правило:

- `.ps1` **с кириллицей** (в строках, комментариях, сообщениях) — обязан быть
  **UTF-8 с BOM**.
- `.ps1` **только из ASCII** — BOM не нужен, кодировка однозначна в любом
  случае. Это осознанный приём: скрипт, который должен пережить любые правки без
  риска (например, глобальный safety-hook — см.
  [Safety Guards](safety-guards.md)), пишут **ASCII-only**, чтобы вообще
  вывести его из-под BOM-ловушки.

> ⚠️ **Это ломает ПАРСЕР, а не только вид текста, и хватает одного эмодзи.**
> Без BOM байты `0x91`/`0x92` (они попадаются внутри многобайтовых символов)
> читаются в cp1251 как «умные» кавычки `'` `'` — а кавычка меняет разбор
> кода. Скрипт падает не на строке с эмодзи, а там, где парсер потерял границу
> строкового литерала, и сообщение указывает мимо. Проверять надо
> **парсибельностью**, а не глазами: правильный текст в редакторе ничего не
> доказывает.

> 🛑 **Особый случай — генераторы, которые ПИШУТ `.ps1`** (скаффолдеры пулов,
> шаблонизаторы). Если генератор пишет файлы без BOM, поломка получает радиус
> «все будущие артефакты»: сам генератор зелёный, дефект видит только тот, кто
> запустит порождённое. Реальный случай: скаффолдер писал `.ps1` без BOM — и ни
> один создаваемый им пул не поднимался вовсе, при этом самотест генератора
> проходил. Правило: **у генератора кодировка выходного файла выбирается по
> расширению** (`.ps1` → UTF-8 **с** BOM), а приёмка гоняется на порождённом
> артефакте, а не на генераторе.

**Рецепт.**

- **Чтение** для анализа — всегда с явной кодировкой:
  `Get-Content -Encoding utf8 -Raw $f`. Без `-Encoding utf8` на ru-RU локали не
  использовать — получишь mojibake ещё на чтении и «почини» несуществующую
  проблему.
- **Правка через Edit/Write-инструмент небезопасна** для `.ps1` с кириллицей:
  наблюдалось, что при сохранении теряется BOM или тело перекодируется в cp1251,
  и после «успешной» правки скрипт не парсится. Поэтому — см. следующий раздел
  про правку байтами, а после любой правки инструментом обязательно проверять
  BOM и парсибельность.

## 2. Правки `.ps1`/текста с кириллицей — байтами, не текстом

**Симптом.** Batch-замена (условно «поменять `.foo\` на `.bar\` в 20 файлах»)
через `Get-Content` → `Set-Content` превращает всю кириллицу в файлах в
mojibake, хотя логика замены верна. `git checkout` не спасает, если файлы были
untracked.

**Причина.** Та же cp1251-неоднозначность (раздел 1), но теперь на цикле
read-modify-write: `Get-Content` без `-Encoding utf8` прочитал UTF-8 как cp1251,
`Set-Content -Encoding utf8` записал обратно уже испорченное. Round-trip
уничтожил данные.

**Рецепт: работать байтами, кодировку задавать явно.**

```powershell
# Batch-safe replace: читаем байты, срезаем BOM, декодируем UTF-8,
# правим, кодируем UTF-8 обратно (с BOM), пишем байтами.
$bytes = [System.IO.File]::ReadAllBytes($f)
if ($bytes.Length -ge 3 -and $bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF) {
    $bytes = $bytes[3..($bytes.Length - 1)]   # отделяем BOM, чтобы не попал в тело
}
$text = [System.Text.Encoding]::UTF8.GetString($bytes)
foreach ($r in $replacements) { $text = $text.Replace($r[0], $r[1]) }
[System.IO.File]::WriteAllText($f, $text, [System.Text.UTF8Encoding]::new($true))  # $true = писать BOM
```

`[System.IO.File]::ReadAllBytes` / `WriteAllBytes` / `WriteAllText` с явным
`UTF8Encoding($true)` не зависят от локали — кодировка не угадывается, а
задаётся. Это единственный надёжный способ для файлов с кириллицей в этом
окружении.

**Проверка после любой правки `.ps1`** (особенно после Edit/Write-инструмента):

```powershell
# 1. BOM на месте? Первые три байта должны быть EF BB BF.
$b = [System.IO.File]::ReadAllBytes($f)
$hasBom = $b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF
# Нет BOM, а кириллица в файле есть → пересохранить с BOM (WriteAllText выше).

# 2. Скрипт вообще парсится? (парс-чек без запуска логики)
$text = Get-Content -Encoding utf8 -Raw $f
[System.Management.Automation.PSParser]::Tokenize($text, [ref]$null) | Out-Null
```

Проверять **до** прогона скрипта — иначе поломку кодировки увидишь как
непонятную ошибку исполнения.

**Восстановление, если кириллицу уже сожгли** round-trip'ом cp1251↔UTF-8 —
обратное декодирование (mojibake прочитать как UTF-8, получить исходные байты
через cp1251, записать назад):

```powershell
$bytes = [System.IO.File]::ReadAllBytes($f)
if ($bytes.Length -ge 3 -and $bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF) {
    $bytes = $bytes[3..($bytes.Length - 1)]
}
$mojibake = [System.Text.Encoding]::UTF8.GetString($bytes)
$original = [System.Text.Encoding]::GetEncoding(1251).GetBytes($mojibake)
[System.IO.File]::WriteAllBytes($f, $original)
```

> Почему рабочие скрипты (`pool.ps1` и пр.) сами выставляют UTF-8 на своём
> stdout: без этого кириллический вывод пришёл бы в контекст модели как
> mojibake. Инструменту, читающему их вывод, отдельно чинить кодировку не
> нужно — она уже задана внутри. См.
> [Pool Communication §7](pool-communication.md) и
> [Wrapper and Hook Scripts](wrapper-and-hook-scripts.md).

## 3. Антивирус душит запуск дочерних процессов (`EPERM: uv_spawn`)

**Симптом.** Любой инструмент, который поднимает процесс — Bash, PowerShell, а
также Glob/Grep (внутри у них `rg`) — **мгновенно** падает:

```
EPERM: operation not permitted, uv_spawn '<exe>'
```

При этом Read / Write / Edit работают (они внутри процесса-харнесса, без
spawn). Перезапуск сессии не помогает. Отключение песочницы
(`dangerouslyDisableSandbox`) тоже не помогает.

**Причина.** `EPERM` (не `ENOENT`) означает: exe найден, но запуск **запрещён
политикой защиты**. Это поведенческий контроль антивируса (в наблюдавшемся
случае — Kaspersky): агентная сессия молотит частым spawn'ом `powershell` / `rg`
из-под `node.exe`, эвристика читает это как скрипт-абьюз (LOLBin) и относит
конкретное дерево процессов в ограниченную группу, где создание дочерних
процессов урезано. Диагностический признак, что дело именно в этом: **другая**
Claude-сессия на той же машине спавнит нормально — значит блок контекстный, по
конкретному дереву процессов, а не машинный и не про образ `node.exe`.

**Рецепт.** Это чинит **владелец машины**, не агент:

- Внести в доверенные программы антивируса корень дерева — `node.exe`
  (`C:\Program Files\nodejs\node.exe`) и заодно `claude.exe`
  (`…\@anthropic-ai\claude-code\bin\claude.exe`).
- Обязательно включить **«применять исключение рекурсивно»** (не контролировать
  и дочерние процессы). Дерево многоуровневое (`node → powershell → cmd →
  tool`); без рекурсии запрет всплывёт на 2–3-м уровне и симптом сохранится.
- После внесения — **перезапустить агента**, spawn оживает. Исключение
  переживает перезагрузку и обновление баз.

Для агента правило простое: **распознал `EPERM uv_spawn` — не чини сам,
эскалируй пользователю** одной фразой «антивирус режет запуск дочерних
процессов, нужно добавить node.exe в доверенные рекурсивно». Диагностировать
заново каждый раз не нужно — симптом однозначный.

## 4. Поисковый инструмент молча пропускает файлы

**Симптом.** Grep-инструмент (и `rg` у субагентов) не находит файлы, которые
**точно** содержат искомый паттерн (проверено прямым чтением).

**Причина.** Комбинация двух факторов: (1) **вложенные git-репозитории** внутри
workspace со своими `.gitignore`-правилами — `rg` уважает ignore и молча
исключает совпадения; (2) связка параметров `path` + `glob` вместе иногда
отсекает часть дерева. Grep при этом **не сообщает**, что что-то пропустил — он
просто возвращает неполный список, и легко принять его за полный.

**Рецепт.** Разделять два разных вопроса:

- «Есть ли это вообще где-нибудь?» — Grep-инструмент отлично годится, он быстрый.
- «Собери **исчерпывающий** список, ничего не потерять» (рефактор по всем
  файлам, аудит ссылок, миграция) — Grep-инструменту **не доверять**. Полный
  инвентарь даёт PowerShell:

```powershell
Get-ChildItem -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\\.git\\|\\node_modules\\|\\\.bus\\' } |
  Select-String -Pattern '<pattern>' -Encoding UTF8 |
  Group-Object Path
```

`Get-ChildItem -Recurse` обходит дерево сам, не спрашивая `.gitignore`, поэтому
вложенные репозитории не скрывают совпадения; `-Encoding UTF8` — чтобы
кириллические паттерны сматчились (раздел 1). Список исключений в
`Where-Object` подгоняй под свой workspace (`.git`, `node_modules`, каталог
шины и т.п.).

Субагенту, который ищет через `rg`, при требовании полноты — велеть грепать
**каждую** вложенную git-подпапку явно, а не полагаться на один проход из корня.

## 5. `-Include` без wildcard в `-Path` не фильтрует — и это удаляет лишнее

**Симптом.** Команда вида «взять из каталога только эти две подпапки» возвращает
**все** подпапки. Если следующим шагом идёт `Remove-Item` — снесено не то, что
предполагалось.

```powershell
# НЕ фильтрует: вернёт ВСЕ каталоги, а не два названных
Get-ChildItem -Path $dir -Recurse -Directory -Include 'alpha','beta'
```

**Причина.** `-Include` применяется к **элементам пути**, а не к результату
обхода, и работает только если сам `-Path` заканчивается wildcard'ом
(`$dir\*`) либо задан `-Recurse` **вместе** с подходящим шаблоном пути. В
остальных случаях параметр молча игнорируется — ошибки нет, вывод выглядит
правдоподобно, просто он полный.

**Рецепт.** Фильтровать явным предикатом, а перед необратимой операцией —
**печатать список**:

```powershell
$victims = Get-ChildItem -Path $dir -Recurse -Directory |
           Where-Object { $_.Name -in @('alpha','beta') }
$victims | ForEach-Object { Write-Host "  удаляю: $($_.FullName)" }   # сначала посмотреть
$victims | Remove-Item -Recurse -Force                                 # потом удалять
```

Общее правило шире одного параметра: **смотреть надо на вывод своей команды, а
не на свою команду**. Уверенность «фильтр же написан» — не доказательство того,
что он сработал.

## 6. Ключи хеш-таблицы регистронезависимы

**Симптом.** Литерал хеш-таблицы, где ключи различаются только регистром,
не компилируется:

```
Duplicate keys 'd:/path' are not allowed in hash literals.
```

**Причина.** Сравнение ключей в PowerShell по умолчанию регистронезависимо, и
`'D:/path'` с `'d:/path'` — один и тот же ключ. Ловушка вылезает именно там,
где регистр несёт смысл: словари замен, таблицы путей, фикстуры для проверки
нормализации регистра.

**Рецепт.** Когда порядок и регистр значимы, брать **упорядоченный список пар**
вместо хеша:

```powershell
$map = @(
    [pscustomobject]@{ From = 'D:/path'; To = '<root>' }
    [pscustomobject]@{ From = 'd:/path'; To = '<root>' }
)
```

Побочная выгода: список задаёт **порядок применения**, а он в заменах обычно
значим (длинные ключи должны идти раньше коротких, иначе короткий разрежет
длинный на куски).
