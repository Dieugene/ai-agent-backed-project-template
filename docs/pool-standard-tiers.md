# Pool Standard Tiers (L1 / L2) и конвенции именования

Как «упаковать» координационный стандарт пула так, чтобы **рабочий агент**
читал минимум, а полная спека оставалась под рукой у сопровождающего. Плюс
конвенции имён wrapper'ов и адресации сообщений. Читать — когда заводишь пул,
пишешь agent-facing документацию (`CLAUDE.md`, onboarding-файлы) или ловишь,
что у агентов раздувается контекст «от одного чтения стандарта».

> Обезличено плейсхолдерами: `<workspace-root>`, `<pool-name>`, `<role>`,
> `<subproject>`, `<tag>`. Примеры из практики обобщены.

---

## 1. Проблема: «прочитай §X» превращается в «прочитай весь стандарт»

Координационный стандарт пула ([Pool Communication](pool-communication.md) —
опоры, шина, hook, lifecycle) в развёрнутом виде объёмен: в практике единый
файл дорос до **~25k токенов**. Когда onboarding-файл агента звал его «читать,
особенно §N», агент по факту открывал файл **целиком** — и эти 25k оседали в
контексте **каждого** peer'а на старте, повторяясь у всех ролей пула.

При том рабочему агенту из всего стандарта нужен **операционный минимум**:
какие команды `pool` есть, что делать после `/compact`, как вести себя с
вотчером, какие инварианты держит инструмент. Остальное (env vars, детали
identity/launch, устройство шины, регистрация hook'а, диагностика, тиражирование,
обоснования решений) нужно тому, кто **заводит или чинит** пул, — и то по одной
конкретной части за раз.

Отсюда — расслоение на два тира.

---

## 2. Два тира

| Тир | Файл | Объём | Кто читает |
|-----|------|-------|-----------|
| **L1 — операционный** | `COORDINATION.md` (рядом с общей pool-CLI) | ~1.7k токенов | **рабочий агент** в пуле |
| **L2 — справочная спека** | `standards/agent-pool-communication-standard.md` (stub-индекс) + `standards/pool/01..07-*.md` | stub ~700 токенов + части | сопровождающий / при заведении пула / за одной деталью |

### L1 — `COORDINATION.md`

Компактный рабочий справочник. Содержит **только то, что нужно в работе**:

- таблица команд `pool` (`send` / `reply` / `note` / `inbox` / `mine` /
  `claim` / `ack` / `dismiss` / `board` / `watch`);
- «тарелка» после `/compact` — `pool mine` (что взято в работу, что ждёт);
- вотчер: как взвести, политика роли (взводить или нет);
- инварианты, которые держит **инструмент, а не память агента** (сообщение =
  файл, адрес = папка, `claim` атомарен, id не переиспользуются).

Открывается строкой-алиасом на общий скрипт и берёт `owner`/`BusRoot` из env —
никаких путей и настроек агенту помнить не нужно. **Это всё, что нужно рабочему
агенту**; L2 он не открывает.

### L2 — stub-индекс + `standards/pool/01..07`

Прежний монолитный стандарт разрезан на части и заменён **stub-индексом**
(~700 токенов): короткая карта «§N → файл», по которой открывают **нужную**
часть, а не весь документ. Части (нумерация ссылок сохранена — заголовки
`## N.` живут внутри):

| Часть | Тема |
|-------|------|
| `01-overview` | TL;DR, опоры системы, отказ от scratch-pads |
| `02-architecture` | модель, инварианты, персистентное состояние |
| `03-identity-launch-routing` | owner/display name, env vars, auto-resume, routing CLAUDE.md |
| `04-bus` | устройство maildir-шины, формат сообщения, lifecycle |
| `05-hook-watcher` | UserPromptSubmit hook, push-watcher, борд |
| `06-lifecycle-peers` | inter/intra-project топология, зоны, риски |
| `07-ops-scaffolder` | дворник личных todo, скаффолдер, эксплуатация |

Архитектурные доки того же порядка (например [Workspace
Organization](workspace-organization.md), ~13k) тоже относятся к L2 — их не
кладут агенту «на прочитать целиком».

> В этом публичном репозитории [Pool Communication](pool-communication.md)
> служит развёрнутым эквивалентом L2, а его врезки/résumé-таблицы — эквивалентом
> L1. Тиринг ниже — про то, как та же информация **упакована внутри живого
> workspace** ради минимального контекста агента.

## 3. Правило маршрутизации: agent-facing → только L1

Единственное правило, которое держит экономию:

> **Все agent-facing документы ведут ТОЛЬКО на L1.**

Agent-facing — это то, что агент читает на старте по routing'у:
`<subproject>/CLAUDE.md`, `_agent_pool_setup-<owner>.md`,
`_agent_pool_identity`-блоки. В них ссылка на координацию — **только**
`COORDINATION.md` (L1). Ссылки на L2 из agent-facing файлов **не ставят**: иначе
агент пойдёт по ним и снова затянет тяжёлую спеку.

Обратное правило для сопровождающего:

- **agent-facing** правка (onboarding, CLAUDE.md, шаблоны) → ссылайся на L1;
- **maintainer/архитектурная** правка → можно на L2 (нужную часть).

Скаффолдер нового пула генерит onboarding уже «чистым» — со ссылкой на L1.
`§N`-цитаты в maintainer-доках остаются валидны: stub-индекс маршрутизирует
`§N` → файл, а заголовки `## N.` сохранены внутри частей.

База per-turn инжекта и так близка к нулю: баннер `[POOL INBOX]` короткий, а в
обёртках стоит `POOL_INBOX_QUIET=1` (пустой баннер не инжектится). Тиринг
убирает именно **стартовый** разовый вес «чтения стандарта».

## 4. Naming-convention

Отдельный, но родственный слой стандартизации: как называть wrapper'ы и как
адресовать сообщения, чтобы семейство пулов не превращалось в кашу.

### Wrapper-батники: `claude-<tag>-<role>.bat`

Формат — **подпроект первым, роль второй**: `claude-<tag>-<role>.bat`.

- `<tag>` — короткий тег подпроекта/пула (kebab-case);
- `<role>` — из стандартного набора: `tl` / `dev` / `qa` / `architect` /
  `benchmark` / `devops`.

Owner ID может быть **короче** тега у мини-проектов внутри семейства
(tag = `<tag>-benchmark` → owner = `<role>-benchmark`, без приставки). Маппинг
tag → owner держат в `scripts/README.md`, чтобы не гадать.

Единый префикс `claude-` и порядок «подпроект-роль» дают предсказуемую
сортировку в проводнике: все wrapper'ы одного подпроекта стоят рядом.

### Адресация: ящик на получателя, без общего плоского inbox

Ключевой принцип — **разделение по получателю**, не общий плоский лоток:

- в maildir-шине это дано **структурно**: у каждого агента свой каталог
  `<bus>/<owner>/`, `send` кладёт файл в `<bus>/<получатель>/new/`. Адрес =
  папка (см. [Pool Communication §4](pool-communication.md));
- в прежней (Tasks-API) схеме тот же принцип держали руками: per-subproject
  mailbox-subdir `.inbox/<subproject>/` **по подпроекту получателя** (payload
  клали в subdir адресата, не свой).

**Почему не общий плоский inbox:** он не масштабируется на семейство —
контекстный шум, коллизии имён payload'ов, невозможно чистить по одному
подпроекту. Шина решает это тем, что ящик = каталог owner'а. Историческое
исключение из практики: один legacy-подпроект сохранил суффикс `-pool` в имени
subdir (`.inbox/<subproject>-pool/`), потому что десятки payload'ов уже лежали
там; новые подпроекты — без суффикса, имя subdir = имя папки подпроекта.

### Бэклог — не через `TaskCreate`

«Задача на будущее» (idea / wishlist / wontfix) — **не** сообщение и **не**
личный todo:

- не `pool send` (это не адресованная кому-то работа сейчас);
- не `TaskCreate` (замусорит стор и, в Tasks-API-эпоху, чужой inbox);
- а строкой в `<subproject>/00_docs/backlog.md`.

Так отложенное не создаёт ложных pending-сигналов и живёт в репозитории
подпроекта, а не в эфемерном сторе задач.
