# Перенос workspace на Linux

Что ломается, когда инфраструктура, выросшая на Windows, едет на сервер, — и **какие артефакты
переносятся как есть, какие требуют серверной версии, а какие не едут вовсе**.

> Аудитория — инженер, поднимающий такое же пространство на Linux-сервере (или ведущий обе
> платформы разом). Пути и имена обезличены плейсхолдерами.
> Родственные документы: [Windows / PowerShell Pitfalls](windows-powershell-pitfalls.md),
> [Wrapper and Hook Scripts](wrapper-and-hook-scripts.md),
> [Self-Testing and False Greens](self-testing-and-false-greens.md).

---

## 1. Решение, которое стоит принять первым: один файл на две платформы

Соблазн — завести серверную ветку кода и править её отдельно. **Не стоит:** ветка расходится молча,
и обе стороны при этом видят зелёные тесты, каждая на своей половине.

Рабочая модель: **общий код один**, платформенные различия — развилками внутри него, и каждая
развилка проверяется с обеих сторон.

Практическое следствие: правки для сервера идут ревью на «родной» платформе, а правки для Windows —
сухим прогоном на сервере. Ни одна сторона не принимает свою половину сама.

## 2. Классы отказов, каждый пойман живьём

Общее у них то, что **на Windows все они зелёные и выглядят верными**.

### 2.1. Обязательных блокировок файлов на Linux нет

`FileShare::None` там не держит ничего: открытый дескриптор никому не мешает. Фоновый процесс,
следящий за входящими сообщениями ([вотчер](board-and-watcher.md)), спокойно **удалил** файл,
который на Windows был бы защищён, и следующее чтение уронило весь прогон.

Правило шире одного случая: **логика, опирающаяся на «файл занят», на Linux не переносится.** Там
неудаляемость даётся правами на **каталог** — удаление и создание записи это его дело, а не файла.

### 2.2. Обратный слэш — легальный символ имени файла

`Join-Path <bus> '.activity\act-<role>'` на Linux создаёт **файл** с таким именем в корне, пока
остальной код работает в каталоге `.activity/act-<role>/`.

Коварство в том, как это выглядит в проверках: часть краснеет ложно, а часть **зеленеет на чём
угодно** — файла, который они проверяют, никто не трогает. ⇒ Составные пути собирать вложенными
`Join-Path`, никогда не зашивать разделитель в строку.

### 2.3. Предохранители знают формы только своей платформы

Отдельный случай, потому что отказ здесь **не в переносимости кода, а в переносимости смысла**.
Предохранитель, предупреждающий об убийстве процессов «по имени», был написан на Windows и знал
`taskkill /IM`, `Stop-Process -Name`, конвейер из запроса в остановку. На Linux тот же класс ошибки
пишется иначе — `pkill -f <шаблон>`, `killall`, `pgrep … | xargs kill`, `kill $(pgrep …)` — и **не
ловился ни одним паттерном**.

Цена выше, чем кажется: на машине агентов все роли — процессы одного пользователя с одинаковым
именем, поэтому одна такая команда кладёт всю смену разом.

⚠️ **И проверять это надо на обеих платформах, а не там, куда переносишь:** если на рабочей машине
установлен эмулятор unix-окружения (у нас `pkill` доступен), слепая зона существует и дома — просто
её никто не искал.

### 2.4. Мелочи среды, каждая из которых валит прогон до первой проверки

| Что | На Windows | На Linux |
|---|---|---|
| `-WindowStyle` у `Start-Process` | работает | **бросает исключение** |
| `$env:TEMP` | заполнена | **пуста** → нужен `TMPDIR`, затем `/tmp` |
| `/tmp` | — | **общий на всех пользователей**: файл с фиксированным именем окажется чужим |
| `-ExecutionPolicy` | нужен | **не существует** |
| интерпретатор | `powershell` | путь берётся у текущего процесса, фолбэк `pwsh` |

Определять платформу так, чтобы это работало и под PowerShell 5.1 (где `$IsWindows` **не
существует**), и под строгим режимом, где обращение к неизвестной переменной бросает:

```powershell
$OnWin = $true
try { $v = Get-Variable -Name IsWindows -ErrorAction SilentlyContinue; if ($v) { $OnWin = [bool]$v.Value } } catch { }
```

### 2.5. Идентичность процесса считается иначе

Проверка «тот ли это процесс, что записан в локе» на Windows опирается на метку времени старта
(`StartTime.Ticks`). На Linux её нет — идентичность собирается из поля 22 в `/proc/<pid>/stat`
и `btime`.

Две ловушки, обе тихие:

- **`StartTime` может вернуть `$null` без исключения** — для чужих процессов, к которым нет доступа.
  На обычной рабочей машине под непривилегированным пользователем это **примерно каждый третий
  процесс** (замер: 143 из 474). Код, сравнивающий метки, должен отличать «метки не совпали» от
  «метку не удалось прочитать», иначе сторож числится живым по бумаге;
- **зомби-процесс читается как живой**: запись в `/proc` есть. Состояние `Z` надо обрабатывать
  явно.

⚠️ **И сам разбор `/proc/<pid>/stat` — отдельная ловушка, на которой порт уже спотыкался.** Строка
устроена как `pid (comm) state …`, причём `comm` может содержать пробелы и скобки. Разбор «по
пробелам с начала строки» даёт первым полем **pid**, а не состояние — проверка «состояние равно `Z`»
не срабатывает никогда, и зомби снова числится живым. Читать надо **после последней закрывающей
скобки**:

```python
tail  = raw[raw.rindex(')') + 1:].split()
state = tail[0]                 # именно состояние, а не pid
```

Фикстура для теста обязана содержать имя команды **с пробелом и скобкой** — на «хорошем» имени
ошибочный разбор выглядит правильным. Дефект приехал в присланном патче и был бы принят: код
читался осмысленно, а поле оказалось не то.

### 2.6. Дефект живёт в ветке, которая короче

Платформенная развилка, возвращающая **массив из одного элемента**, на выходе `if` молча становится
строкой — и следующая конкатенация склеивает флаги в одну строку. Дочерний процесс тогда просто не
стартует, а симптом выглядит как «расхождение меток процесса».

```powershell
function Get-PSFlags([bool]$onWin) {
  [string[]]$fl = if ($onWin) { @('-NoProfile','-ExecutionPolicy','Bypass') } else { @('-NoProfile') }
  return ,$fl        # ведущая запятая: без неё PowerShell разворачивает одноэлементный массив обратно
}
```

⇒ И проверять надо **обе** ветки — тем, что после конкатенации считается **количество элементов**.
Такая проверка ловит класс ошибки на Windows, не выезжая на целевую платформу.

### 2.7. Правка ASCII-файла с Linux портит его незаметно для правящего

`pwsh` читает UTF-8 и мусора не показывает, а PowerShell 5.1 файл **без BOM** читает в системной
однобайтовой кодировке (на русской локали — cp1251). Нелатинский комментарий, вписанный с сервера в
общий скрипт, ломает его на Windows — и правивший этого не видит. Подробности режимов кодировки —
[Windows / PowerShell Pitfalls](windows-powershell-pitfalls.md).

## 3. Главный системный вывод: измеритель отстаёт от измеряемого

На старте переноса ядро шины портировали, а **самотест — нет**: он остался с зашитыми
windows-путями внутри. Пока это не починили, «зелёный самотест на сервере» **не значил ничего**.
(В матрице §4 самотест уже числится переносимым — это состояние **после** починки, и оно наступило
позже ядра, хотя должно было раньше.)

> **Портируя инструмент, портируй первым то, чем его проверяют.**

## 4. Матрица переносимости артефактов

Классификация — по фактическому содержимому: есть ли внутри вызовы, которых на Linux нет
(управление деревом процессов, оконный терминал, реестр, `.bat`-обёртки).

### 4.1. Едет как есть

| Артефакт | Почему безопасно |
|---|---|
| Ядро шины ([`pool.ps1`](pool-communication.md)) | портировано, развилки внутри, проверяется на обеих платформах |
| Приёмочный самотест шины | портирован вслед за ядром, печатает платформу в сводке |
| Модуль памяти роли ([что это](agent-long-term-memory.md)) | платформенные развилки внутри, пути собираются `Join-Path` |
| Хуки памяти: аудит перед сжатием и впрыск после | вызывают только файловые операции; интерпретатор и путь **вычисляются**, а не зашиты |
| Проверки структуры памяти | чистая работа с текстом |
| Блокировщик катастрофического `rm` ([Safety Guards](safety-guards.md)) | разбирает текст команды, файловой системы не касается — уехал без единой правки |
| Каноны, стандарты и тексты команд | текст |

⚠️ **Вместе с каталогом инфраструктуры обязательно везти файл-флаг раскатки памяти.** Без него роли
на сервере стартуют с общей памятью и без хуков сжатия — **молча**.

### 4.2. Требует отдельной серверной версии

| Артефакт | Что именно не переносится |
|---|---|
| Контроллер завершения пула ([что это](pool-shutdown-and-context-refresh.md)) | завершение дерева процессов, работа с окнами терминала |
| Скаффолдеры пула и добавления роли ([что это](pool-scaffolding.md)) | генерируют `.bat`-обёртки и конфиг вкладок |
| Обёртки ролей ([что это](wrapper-and-hook-scripts.md)) | `.bat` → shell-скрипт |
| Предохранитель против убийства чужих процессов ([Safety Guards](safety-guards.md)) | матчер знал только windows-формы: `pkill`, `killall`, `pgrep \| xargs kill` не ловились ни одним паттерном |
| Детектор искажённого вывода ([Safety Guards](safety-guards.md)) | всплывающее уведомление; на машине без графической среды заменяется файлом-сигналом, который читает пульт |
| Глобальные предохранители, зарегистрированные в хуках движка | пути и интерпретатор зашиты под Windows |

⚠️ **Две вещи, которые выглядят непереносимыми, но серверной версии не требуют** — проверено на живом
пуле:

- **пикер пулов** остаётся на рабочей машине и поднимает удалённые роли **через обычные обёртки, внутри
  которых `ssh`**. Раскладка при этом строится штатно из манифеста, и вместе с ней приезжают метка
  живости, предохранитель от повторного запуска и остальные пункты меню. Заводить второй генератор
  раскладок под сервер — значит завести вторую ветку того же кода;
- **доска в отдельном окне** не переносится, а **заменяется** пультом внутри панели: отдельное окно на
  машине без графической среды смысла не имеет.

⇒ Общее правило: прежде чем писать серверную версию, проверь, не решается ли задача **тем же
инструментом с другой командой внутри обёртки**.

**Не едет вовсе** только то, чему на сервере нет применения: настройки рабочей машины (тема, голос,
интеграции с GUI) и профили браузера для агентов — последние понадобятся, лишь если на сервере
поднимается роль, которой нужен браузер.

### 4.3. Настройки движка, которые надо перенести явно

Их легко забыть, потому что они не файлы проекта, а пользовательская конфигурация. Проверять
поимённо:

- каталог `commands/` — иначе слэш-команды (включая сверку памяти) на сервере **отсутствуют**;
- хуки-предохранители — каждый требует серверной версии, см. 4.2;
- уровень усилий модели — **не задан по умолчанию**, и роли молча работают на дефолтном;
- список включённых плагинов — не задан ⇒ плагины на сервере выключены;
- переопределения скилов;
- список разрешённых инструментов.

### 4.4. Обёртка роли на shell: три мины наследования

`.bat`-обёртка стартует в чистом окружении, а shell-обёртка обычно **сорсит общий файл** и потому
наследует переменные — от предыдущей роли, от родительской оболочки, от чужого запуска. Три вещи,
которые надо сделать явно:

1. **Гасить переменные роли ПЕРЕД сорсингом общего файла.** Иначе значение соседа доезжает до
   текущей роли молча — она стартует с чужой конфигурацией, и никакая проверка постфактум этого
   не покажет.
2. **Признак «не задавать» должен быть словом, а не пустотой.** Если в конфиге пустая строка уже
   означает «не указано», то ею нельзя выражать «указано: ничего не пинить» — иначе два разных
   намерения неотличимы. Явное значение (`none`, `-`) снимает двусмысленность; пустая строка при
   этом — законный повод **отказаться со внятной ошибкой**, а не молча продолжить.
3. **При «не пинить» — ещё и снять переменную движка.** Не задать своё ≠ не иметь значения:
   переменная может прийти из окружения и включить то, что роль намеренно выключала.

Плюс мелочь, которая портит жизнь при повторных запусках: блок правки `PATH` делается
**идемпотентным** — иначе каждая новая сессия дописывает тот же каталог ещё раз.

### 4.5. Две копии одного файла расходятся молча

Как только у общего кода появляется серверная копия, между ними заводится дрейф: правку внесли в
одну, а вторая живёт прежней жизнью — и узнаёшь об этом, когда поведение отличается. Реальный
случай: защита, добавленная в рабочей копии, до серверной не доехала вовсе, и там сторож работал
по старой логике месяц.

⇒ **Прежде чем чинить поведение на одной из машин, сверь копии** (хеш файла или дату правки), и
только потом делай вывод о причине. И наоборот: закончив правку общего кода, сразу назови, кто и
когда перенесёт её во вторую копию, — «перенесу потом» здесь означает «не перенесёт никто».

## 5. Как проверять платформенный код, не имея второй платформы под рукой

Приёмочный самотест общего кода строится так, чтобы **обе ветки развилки** проверялись всегда:

- **обе ветки платформенных флагов** проверяются на любой платформе — счётом элементов после
  конкатенации (см. 2.6);
- проверки, ищущие **windows-специфичное явление**, на Linux законно пропускаются — тогда разница в
  числе прошедших проверок объяснима, а **платформа печатается в строке сводки**, чтобы «77 из 77»
  и «76 из 76» не выглядели расхождением;
- любой самотест **возвращает ненулевой код**, если хоть одна проверка провалилась, — иначе его
  нельзя поставить гейтом;
- проверка комплектности каталога вычитывает **имена соседних скриптов из самого кода** (по
  вызовам), а не хранит их списком: список устаревает молча.

Остальные правила приёмки — не делать обязательным законно отсутствующее, учить проверку объяснять
себя, проверять новый тест мутацией — общие для любой платформы и собраны в
[Self-Testing and False Greens](self-testing-and-false-greens.md).
