# Pool Shutdown and Context Hygiene

Как **внешний контроллер** (и единый пульт-пикер) корректно завершает и
освежает сессии агент-пула: снимает их со сторожами без сирот, делает handoff
и compact на осмысленных основаниях — вместо того чтобы человек «дежурил» у
момента `/compact`. Это надстройка над [pool-шиной](pool-communication.md),
[вотчером/бордом](board-and-watcher.md) и [пикером](pool-launcher-and-warp.md).

> Это описание паттерна, не инструкция под конкретный проект. Все
> идентификаторы (имена пулов, ролей, пути) — плейсхолдеры вида
> `<workspace-root>`, `<user-home>`, `<pool-name>`, `<slug>`, `<owner>`,
> `<role>`, `<session-id>`. Рабочий код: контроллер завершения —
> [../scripts/pool-shutdown.ps1](../scripts/pool-shutdown.ps1); пикер-пульт —
> [../scripts/launch-pool.ps1](../scripts/launch-pool.ps1).

> **Статус (честно).** Сторона **завершения** построена и обкатана (self-test
> зелёный, провалидирована DryRun на живых данных; реальный не-DryRun прогон —
> только по слову пользователя, он гасит рабочие сессии). **Перезарядка роли
> соседом** (§5) — построена и прогнана на живой роли: контекст `56% → 8%`,
> транскрипт не форкнут. Полностью автоматическое **освежение на месте** (без
> остановки процесса) и **автотриггеры** (по заполнению контекста / по
> расписанию) — **спроектированы, но не достроены**. Что где — в §7.

## 1. Зачем — автономные самоочищающиеся агенты

Цель — сессии, которые **сами** передают состояние, сжимаются и завершаются на
надёжных основаниях, а не по ручному вмешательству в конкретный момент.
Сегодня `/compact` — лоссовое сжатие, которое человек запускает «на глаз»,
подгадывая, пока контекст ещё не деградировал; handoff перед ним — дисциплина
агента. Оба шага держатся на присутствии человека у клавиатуры.

Контроллер выносит эти шаги во **внешнюю управляющую систему пула**, которая
(а) пробрасывает в сессии команды (в т.ч. слеш-команды вроде `/compact`) и
(б) выполняет операции для пула — запуск / остановку / освежение нужных
сессий. Стратегически это ступень к **автономному, в перспективе серверному**
контуру: тот же «кирпич» завершения, вызванный без человеко-гейта, — уже
основа для сервера, который сам решает, когда роль пора освежить.

Рамка: до **auto-compact сознательно не доходим** — освежаем раньше, по своим
основаниям. Диагностика **деградации** контекста (решение о полном `clear` /
пересадке в свежую сессию) пока за человеком и вне скоупа.

## 2. Метрика контекста — tee статус-лайна → per-session ctx-JSON

Контроллеру нужна свежая карта «какая сессия насколько заполнена», получаемая
**без участия самих агентов**. Источник — вход статус-лайна: перед каждой
отрисовкой CLI передаёт скрипту статус-лайна на stdin JSON с полями сессии.
Одна строка **`tee`** в этом скрипте пишет вход в файл-на-сессию:

```
<user-home>/.claude/.control/ctx-<session-id>.json
```

tee добавляет `agent_owner` (из env сессии) и `stamped_at`; работает
**best-effort** — статус-лайн не ломает, при сбое просто нет свежего файла.
Живёт **глобально**, для всех сессий workspace.

| Поле | Смысл |
|------|-------|
| `session_id` | UUID сессии (глобально уникален → pool-safe идентификатор). |
| `session_name` | Display-name (title) сессии. |
| `cwd` | Текущая рабочая директория (может «дрейфовать», если агент сделал `cd`). |
| `agent_owner` | `<owner>` из env — чья это сессия. |
| `context_window.used_percentage` | **Загрузка контекста в %** — главное основание. |
| `stamped_at` | UTC-метка записи (возраст файла = свежесть метрики). |

Контроллер читает **все** `ctx-*.json` в карту живых сессий и сопоставляет
цели пула по `agent_owner` **и** по тому, что `cwd` лежит **под корнем пула**
(равен корню или его подкаталог). cwd-фильтр критичен: у разных пулов бывают
**одинаковые имена ролей** (`lead`/`operator`/`builder`), и без него owner-имя
схватило бы чужую сессию.

Метрика может отсутствовать (сессия idle или поднята до внедрения tee).
Контроллер это ловит: сверяет число живых `claude.exe` с числом сессий в
метрике и для «слепых» делает **фолбэк по display-name** из wrapper'а роли
(`title → UUID → живой процесс`), чтобы не пропустить молча живую сессию.
Неизвестный контекст трактуется **консервативно — как повод для handoff**.

## 3. Двухфазное завершение (контроллер)

Контроллер разбивает завершение на две фазы с **человеко-гейтом** между ними:
сперва handoff у ВСЕХ целей, и только после подтверждения — гашение. Ключ
`-Full` прогоняет обе фазы одним вызовом (батчем, без ручного гейта).

### 3.1 Фаза 1 — handoff по шине + гейт

По каждой цели с живым процессом и контекстом **на пороге или выше** (§4):

1. Контроллер пишет метку `<user-home>/.claude/.control/shutdown-intent-<owner>`
   — «момент Фазы 1» (нужен для гейта свежести, §3.5) — и удаляет любой
   устаревший ready-флаг.
2. Кладёт в шину задачу «заверши работу» через `pool send` — **половины
   сообщения (payload + адрес-папка) держит сама шина** (см.
   [Pool Communication §4.2](pool-communication.md)). В тело задачи контроллер
   **впрыскивает полный канонический текст** команды
   [handoff-myself](../commands/handoff-myself.md), прочитанный из файла
   команды (project-local приоритетнее глобального) — чтобы агент выполнил её
   **дословно, а не по памяти**. Рамка — checkpoint-handoff: сохранить свежие
   директивы пользователя дословно, вернуть claimed-задачи в шину, по
   готовности поставить флаг.
3. **[Вотчер](board-and-watcher.md) будит** простаивающего агента (push по
   шине). Агент пишет свой `_handoff_<owner>.md`, возвращает недоделанные
   claimed-задачи и создаёт пустой **ready-флаг**
   `<user-home>/.claude/.control/shutdown-ready-<owner>`.

Разослав задачи всем, контроллер ждёт флаги **параллельно** — один общий
дедлайн, опрос каждые 5 с (а не N × таймаут). Затем печатает сводку и
**останавливается**: гашения в Фазе 1 нет, дальше — по команде оператора
(`-KillOnly`). Опциональный `-Seal` после флагов глушит источники побудки
(вотчер + Telegram-sentinel) по PID, оставляя `claude` живым, — стабилизирует
«готов» на время гейта (оптимизация, не гарантия; корректность держит хук).

### 3.2 Фаза 2 — гашение + compact

Гасятся только **подтверждённые** цели. По каждой: проверить свежесть флага
(§3.5) → **taskkill** дерева (§3.3) → **headless compact** (§3.4). Что именно
делается — зависит от контекста цели:

| Контекст цели | Фаза 1 | Фаза 2 |
|---------------|--------|--------|
| `≥` порога (по умолч. 12%) | handoff по шине + флаг | kill + compact |
| `<` порога (известен) | пропуск — **лёгкое закрытие** (§4) | только kill (без compact) |
| неизвестен (нет метрики) | handoff (консервативно) | kill + compact |

### 3.3 Гашение: `taskkill /F /T` от лаунчера, не `Stop-Process`

Гасить сессию нужно **вместе с её фоновым хвостом** — вотчером, Telegram-
sentinel'ом, прочими фоновыми задачами. Иначе контроллер оставит за собой
сирот, которые продолжат будить мёртвую сессию.

| Способ | Что происходит | Вердикт |
|--------|----------------|---------|
| `Stop-Process -Id <claude>` | `claude` мёртв, а вотчер/sentinel/фоновые дети **живы** (сессия поднята вне job-объекта, родитель `WmiPrvSE`). | **Запрещён** — оставляет сирот. |
| `taskkill /F /T /PID <pid>` | Сносит **всё дерево** (сессия + вотчер + sentinel + фоновые). Сирот нет ⇒ локи парсить не нужно (они заведомо неполны). | **Единственный** способ. |

Бить контроллер целится не в `claude`, а в **cmd-лаунчер окна**: идёт вверх от
`claude` до ближайшего `cmd.exe`, крутящего `.bat` роли, и `taskkill /F /T` по
нему — тогда валится `cmd → powershell → claude + дети` **И закрывается окно**
терминала (`.bat` не доходит до `pause`). Если лаунчер не найден — фолбэк на
дерево `claude` напрямую (окно останется на `pause`).

**Инварианты.** Себя контроллер не гасит (гард по ancestry от своего PID).
Цель ищется по PID конкретной сессии, **никогда по имени/маске** — рядом живут
чужие пулы. **Мосты (remote-bridge) не трогаются** — они вне дерева сессии
(родитель `WmiPrvSE`), `/T` их не достанет; это правильно, мост живёт per-бот.

### 3.4 Compact: headless и **детачный** (WMI)

После гашения контроллер сжимает сессию к следующему старту:

```
claude --resume <uuid> --dangerously-skip-permissions -p "/compact"
```

Тонкости, без которых не работает:

- **Только из PowerShell** — Git Bash ломает `/compact`, конвертируя
  аргумент-со-слешем в путь (MSYS).
- **cwd = каталог проекта** сессии; корень берётся из **манифеста**, не из
  дрейфующего `cwd` агента.
- Имя резолвится в **новейший** (= активный) UUID самим контроллером —
  headless `--resume <name>` при неоднозначности падает (нет пикера).
- Запуск **детачно** через `WMI Win32_Process.Create`: родитель процесса —
  `WmiPrvSE`, вне job окна ⇒ compact **переживёт закрытие терминала** (можно
  закрыть окно пула сразу после фазы kill). Запускается через `.bat` со stdin
  из `NUL` (иначе headless `claude` виснет на stdin) и информативным баннером
  в заголовке окна, чтобы задетаченный compact не выглядел «пустым
  терминалом»; окно закрывается само по завершении.

Fire-and-forget: контроллер не ждёт конца. Проверить, что compact реально
записался, можно по появлению `compact_boundary` в хвосте транскрипта.

### 3.5 Ключи: `-Full`, `-Only`, гейт свежести флага

- **`-Full`** — весь цикл одним вызовом, **батчем**: все handoff → все флаги →
  все kill+compact, без ручного гейта. Безопаснее пер-таргетного
  последовательного: **никого не гасим, пока не готовы ВСЕ**. Компакты детачны,
  переживают закрытие терминала. Для будущего автономного сервера — тот же
  кирпич без гейта.
- **`-Only <roles>`** — подмножество ролей **внутри** `-Pool` (pool-scoped, без
  неоднозначности `-Owner`). Так пульт завершает «выбранные роли».
- **Гейт свежести флага** — **устаревший handoff-флаг не должен
  авторизовать kill**. `ready` валиден только если **новее** `intent`-метки
  Фазы 1. Ловит два случая: (а) флаг из прошлого цикла / после рестарта;
  (б) агент **поработал после handoff** — тогда хук `UserPromptSubmit`
  (source-agnostic авто-очистка на любом новом ходе) уже стёр `ready`, и цель
  корректно не гасится. Невалидный флаг → пропуск (нужен `-Force`, чтобы гасить
  всё равно).

### 3.6 Карантин гашения — пока идёт handoff, роли не шлют ничего

Требование заказчика было сформулировано так: «с момента начала гашения вотчеры
и сторожа перестали вбрасывать данные — чтобы я не опасался, что пока идёт
handoff, прилетит новая задача или сообщение». Иначе агент, уже написавший
`_handoff_<owner>.md`, получает свежий ход, и сохранённое состояние устаревает
в момент своего создания.

Карантин держит та же `intent`-метка Фазы 1: пока она лежит, источники побудки
(вотчер шины и sentinel чата) переходят в режим «слышу только контроллера».
Три детали здесь несущие — каждая куплена отдельным дефектом:

1. **Метка ставится ПОСЛЕ отправки задачи завершения.** Поставить раньше —
   значит заглушить ту самую задачу, ради которой роль будят.
2. **Контроллер проходит сквозь карантин.** Фильтр не «молчать обо всём», а
   «пропускать отправителя-контроллера»: задача завершения приезжает роли той
   же побудкой, и глухой карантин подвесил бы гашение до таймаута. Замер:
   сторож опрашивает шину раз в 20–45 с, метка встаёт за миллисекунды — то
   есть перестановкой порядка записи это НЕ лечится, лечится только фильтром.
3. **Под карантином не трогается реестр прочитанного.** Реестр подавляет
   повторные разовые пинги; отметить проглоченный под карантином пинг
   «виденным» — значит, что он не разбудит роль уже никогда.

Прервали гашение на полпути — метка остаётся, и роль будет глухой. Поэтому её
**снимает запуск пула**: чистка стоит в пикере ДО открытия окна (иначе роль
стартует ещё в карантине и молча не слышит шину).

### 3.7 Роль без экрана: контроллер её не увидит

Отдельный отказ, который стоит знать заранее. Если окно терминала снято
средствами ОС (диспетчер задач), процессы под ним **продолжают жить**: сессия
работает, вотчер тикает, но экрана у неё больше нет — впрыснуть ей ход
некуда. Признак такой роли — три условия сразу, и третье куплено замером
(пять срабатываний, все пять — мёртвые сессии):

* письмо в шине новее последнего хода роли;
* вотчер взведён (свежий heartbeat в его локе);
* **процесс жив**.

Штатное гашение такую роль не спасает и не находит: контроллер сопоставляет
цель с процессом по имени сессии в командной строке — если процесс уже снят,
он честно печатает «процесс не найден», а если процесс жив, то роль всё равно
не ответит на handoff-задачу, потому что читать её некому. Практический вывод:
**закрывать роли пультом, а не диспетчером задач**; а если уже закрыли —
остаётся снять оставшиеся деревья процессов и поднять роли заново (сессии
восстанавливаются по имени, история не теряется).

## 4. Лёгкое закрытие по порогу контекста

Не всякую сессию стоит освежать. Если контекст **известен и ниже порога** (по
умолчанию 12%), в ней нечего сохранять — её просто **закрывают**: без handoff,
без compact. На пороге и выше — полный цикл (handoff + compact). Неизвестный
контекст → консервативно handoff (не знаем нагрузку — могли бы потерять работу).

Это маленький, **проверяемый предикат** в контроллере (по сути: «ctx задан И
`ctx < порога`»), а не эвристика:

| Контекст | Предикат «лёгкое закрытие» | Действие |
|----------|---------------------------|----------|
| `5%` | да | просто гашение |
| `12%` (= порог) | нет | handoff + compact |
| `50%` | нет | handoff + compact |
| неизвестен (`$null`) | нет | handoff + compact |

При лёгком закрытии гейт свежести флага пропускается (флага и не заводили) —
сессия гасится сразу.

## 5. Перезарядка роли соседом (`-Recharge`)

Завершение оставляет роль **выключенной**. Перезарядка — тот же цикл, но роль
после него **поднимается обратно**: `handoff → kill → compact → подъём`. Это и
есть практическая форма «освежения»: контекст сжимается, сессия продолжается с
тем же именем и той же историей.

**Почему это делает сосед, а не сама роль.** Роль не может перезарядить себя —
контроллер не гасит собственного предка (гард по ancestry от своего PID), да и
любая команда после `kill` уже не выполнится. Поэтому операцию проводит
**другая роль того же пула**: у неё есть и доступ к контроллеру, и своя шина,
чтобы принять подтверждение. Для человека это выглядит как «сосед привёл
коллегу в порядок», и ничьё присутствие у клавиатуры не требуется.

**Пять отличий от гашения. Каждое куплено разбором, ни одно не косметика:**

| Узел | Почему именно так |
|------|-------------------|
| Компакт **ждём**, а не детачим | Поднятая роль + ещё пишущий компакт = два процесса на один транскрипт. При гашении детач правилен (никто не поднимается), при перезарядке — порча истории. |
| `intent`-метку снимаем **до** подъёма | Под меткой действует карантин (§3.6): роль поднялась бы **немой** — живой, но не слышащей ни шину, ни чат. |
| Перед подъёмом проверяем, что **живых сессий с этим титулом не осталось** | `taskkill /T` чистит не всё; поднять вторую сессию поверх выжившей — это форк транскрипта, который потом не развести. |
| Обёртку роли проверяем **до** гашения | Иначе роль погашена, а поднять её нечем: ошибка обнаружится в момент, когда откатывать уже нечего. |
| Поднимаем **обёрткой и через WMI** | Прямой запуск сделал бы роль потомком контроллера — она умерла бы вместе с его окном. WMI выносит её из дерева (родитель `WmiPrvSE`), как и детач компакта (§3.4). |

**Приёмку даёт не контроллер, а сама роль**, и признаков два — разной природы:
письмо в шину соседу (техническая приёмка: канал жив, роль слышит) и сообщение
человеку в его канал (человеческая: «я вернулся, контекст такой-то»). Первое
обязательно, второе — потому что тишина после операции читается как отказ.

**Замер боевого прогона:** контекст роли `56% → 8%`, идентификатор сессии тот
же (транскрипт не форкнут), обе приёмки пришли. Отдельный урок предварительной
обкатки: репетиция на одноразовом пуле окупилась дважды — на ней всплыли два
дефекта в смежном коде, без которых операция бы не прошла.

## 6. Пульт — единая точка управления

Чтобы операции над пулом имели **один дом**, они собраны в том же
[пикере-пульте](pool-launcher-and-warp.md) (`launch-pool.ps1`), из которого пул
запускается. Выбрав пул, оператор получает три действия:

| Действие | Что делает |
|----------|-----------|
| **Запустить** | Поднять сессии пула (весь / ведущий / выбранные роли). |
| **Завершить** | `handoff → гашение → compact` в отдельном окне: пикер зовёт контроллер с `-Full -CloseWindow`; при подмножестве — добавляет `-Only <roles>`. Есть шаг подтверждения с явным объёмом («ВЕСЬ пул» / «роли: …»). |
| **Борд** | Открыть/поднять живую [доску пула](board-and-watcher.md). |

Так «завершить пул» и «завершить отдельные роли» находятся там же, где
«запустить», — не нужно помнить путь к контроллеру и его ключи. Пикер только
**зовёт** контроллер (в отдельном окне PowerShell); всю механику фаз держит сам
контроллер.

---

## 7. Сторона «освежение»: что построено, что спроектировано

Скрипт-контроллер — про **завершение**: оставляет сессию остановленной и сжатой
к следующему старту. Симметричная сторона — **освежение на месте** (сжать и
продолжить, не закрывая) — спроектирована, но не достроена.

| Возможность | Статус |
|-------------|--------|
| Двухфазное завершение (handoff → kill → compact) | **реализовано**, обкатано в DryRun |
| Лёгкое закрытие по порогу; гейт свежести; `-Full`/`-Only` | **реализовано** |
| tee-метрика контекста (глобально) + авто-очистка флага хуком | **реализовано** |
| Основание «завершаем работу + ctx ≥ порога» | **реализовано** (детерминированная логика) |
| **Перезарядка роли соседом** (handoff → kill → compact → подъём, §5) | **реализовано**, прогнано на живой роли |
| Освежение **на месте** (compact **без остановки процесса**) | **спроектировано, не построено** |
| Автотриггер по заполнению контекста (напр. 12% / 25%) | **спроектировано, не построено** |
| Автотриггер по расписанию | **спроектировано, не построено** |
| Само-объявление готовности сессией (флаг `checkpoint-ready`, ставит агент по завершении целостного цикла, снимает хук `UserPromptSubmit`) | **спроектировано, не построено** |
| Анти-трэшинг guard (cooldown/breaker против зацикливания автоосвежения) | **спроектировано, не построено** |

Замысел автотриггера (не построен): второе основание — **ctx ≥ 25% И завершён
целостный цикл**. Готовность может объявить только сама сессия (что она не ждёт
ни пользователя, ни peer'ов). Конструкция держит недетерминированность **в одну
сторону**: вопрос задаётся **от обратного** — «есть ли начатые здесь и ещё не
закрытые задачи, ждущие ответа?». Часть проверяема **детерминированно**
(claimed-задачи в шине и in-progress в task-store — это файлы, контроллер видит
их сам); пинг агенту остаётся только для нематериализованных ожиданий и потому
редок. Именно эта наблюдаемая часть (агент может забыть поставить флаг или
поставить преждевременно) — то, что предстоит отлаживать.

Отдельный незакрытый вопрос — **watcherless-роли** (DevOps/серверные,
намеренно без вотчера, см. [Board and Watcher](board-and-watcher.md)): на
bus-handoff они не просыпаются, handoff отваливается по таймауту. Без `-Force`
такая сессия **переживает** завершение (безопасно, но неполно) — нужна
отдельная политика.

## 8. Кроссплатформенность

Текущая реализация — **Windows**: детач compact'а через `WMI
Win32_Process.Create`, гашение через `taskkill /F /T` по cmd-лаунчеру окна.
Идея переносится на **Linux** без изменения сути:

- **гашение** — бить не по агенту, а по **группе процессов / session-leader**
  (`kill` по process-group), чтобы снять сессию вместе с фоновым хвостом
  (аналог `/T`);
- **детач compact'а** — отдельный **systemd-юнит** (или `setsid`/`nohup`),
  чтобы сжатие пережило закрытие терминала (аналог родителя `WmiPrvSE`).

Концепт один и там, и там: **бить от лаунчера, а не от агента**, и **сжимать
детачно**. Именно эта инвариантность — предпосылка серверного, автономного
контура (§1).
