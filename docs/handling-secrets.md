# Handling Secrets

Секрет (`.env`, API-ключ, JWT, приватный ключ), попавший в транскрипт диалога,
вывод команды, лог или отчёт, — считается **утёкшим**: его нужно ротировать, а
часть ключей платная и перевыпускается вручную. Агент постоянно работает рядом с
секретами (деплой, отладка окружения, конфиги), и несколько привычных команд
разворачивают их в открытый вид **незаметно**. Этот документ — про то, как не
устроить утечку по неосторожности.

> Плейсхолдеры: `<PROVIDER>_API_KEY`, `JWT_SECRET` и т.п. — имена переменных,
> **не значения**. Реальные значения в базе знаний не приводятся никогда.

**Главный принцип: проверяй наличие переменной, а не её значение.**

---

## 1. Никогда не выводить содержимое секрета

- Не `cat` / `Read` / `echo` / `Get-Content` / print файлов `.env` и ключей — ни
  в терминал, ни в лог, ни в файл отчёта. Нужно сослаться на секрет — ссылайся
  **по имени переменной** (`<PROVIDER>_API_KEY`), значение подставит система из
  файла.
- Несекретное печатать можно: `DATABASE_URL=sqlite:///./data/x.db`, номера
  портов, имена сервисов.
- Показываешь пользователю лог — вычищай строки, похожие на ключ (длинные
  base64-подобные последовательности, `sk-…`, JWT). Сомневаешься —
  редактируй.

---

## 2. Команды, которые разворачивают секреты в plaintext незаметно

Эти команды выглядят диагностическими, но печатают **разрешённые** значения
секретов. Никогда не запускать их с полным выводом — либо безопасный вариант,
либо пропустить через редактор:

| Опасная команда | Что печатает | Безопасно вместо неё |
|-----------------|--------------|----------------------|
| `docker compose config` | подставляет `env_file` в `environment:` | `docker compose config --no-interpolate` (оставляет `${VAR}`); либо сверять YAML-файлы без рендера |
| `docker inspect <container>` | весь массив `Env` контейнера | `--format '{{.Name}} {{.State.Status}}'` или whitelist полей |
| `docker exec <c> env` / `printenv`, `docker compose run --rm <svc> env` | весь env процесса | не запускать для диагностики; нужна одна переменная — проверять её наличие, не печатая значение |
| `systemctl show <service>` | развёрнутые `Environment=` из env-file | запрашивать конкретные свойства, не весь дамп |
| `kubectl describe pod` / `kubectl get secret -o yaml` | значения секретов целиком | `-o jsonpath` по нужному полю; секреты не дампить |

Общее правило при сомнении: **захвати stdout, вычисти секреты ДО чтения, и
только потом смотри** — не «сначала посмотрю, потом решу».

---

## 3. Передача и хранение

- **Перенос `.env` на сервер** — только шифрованным каналом: тем же ключом и
  host-key, что и SSH-соединение (например, `pscp.exe` поверх того же ключа).
  На месте — `chmod 600`, владелец `root`. Не копировать через промежуточные
  незашифрованные точки.
- **В Docker-образы секреты не запекать.** Только `env_file:` в compose;
  **никогда** `COPY .env` в Dockerfile и `ENV KEY=value` для секретов. Слои
  образа читаются кем угодно, кто может его вытянуть.
- **Образы с секретами не пушить** в реестр — особенно публичный: pull доступен
  всем, слои распаковываются.

---

## 4. Публичный репозиторий и разделение конфигов

- **Секреты и конфиги — раздельно.** Несекретная конфигурация (порты, флаги,
  пути, имена сервисов) может жить в репозитории; секреты — только в `.env`,
  который **в `.gitignore` каждого проекта**. Проверять `.gitignore` **перед
  любой** git-операцией.
- **В публичном репозитории — плейсхолдеры, не значения.** Пример окружения —
  это `.env.example` с `<PROVIDER>_API_KEY=<your-key-here>`, а не реальный
  ключ. Любые пути, домены, IP, имена хостов, имена внутренних проектов в
  публикуемых материалах — обобщать (`<vps-ip>`, `<host>`, `<subproject>`).
- Правило симметрично для документации и примеров команд: если в примере нужен
  секрет — там стоит плейсхолдер и словесное описание, а не живое значение.
